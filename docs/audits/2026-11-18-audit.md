## 3. Open findings

### 3.1 HIGH · C3+C1 — `_persist_in_bg` catches only `CalledProcessError`; sqlite3 paths uncaught — **confirmed present**

**File:** `scripts/mac_analyze_loop.py`, line ~419  
**Class:** C (silent-failure) — C3 honest-counting, C1 honest exit code.

`_persist_in_bg` wraps the persist call in `except subprocess.CalledProcessError`.
However `push_track_rows` (called inside the same thread) makes direct
`sqlite3.connect(SCRATCH_DB)` / `.execute()` / `.commit()` calls. A locked scratch
DB, a corrupt file, or a missing path raises `sqlite3.OperationalError` or
`sqlite3.DatabaseError` — neither is caught. The uncaught exception silently kills
the background thread without calling `counts.persist_failed_inc()`. The main loop
never learns the slot failed; `exit_status()` sees neither a success nor a failure,
so a session where the scratch DB is broken can drain and exit 0 with zero rows
written.

Upgraded from LOW to HIGH because: (a) the scratch DB path is session-relative
and can fail on first access, (b) this is the confirmed-present path, not a
hypothetical, and (c) the same bug was graded LOW in the prior audit under a
narrower reading of the code.

**Fix:** Broaden the except clause to `except (subprocess.CalledProcessError,
sqlite3.Error) as e:` (or `except Exception as e:`), call
`counts.persist_failed_inc()` in the handler as the success path's mirror.

### 3.2 MEDIUM (new) · C1 — `ingest/main.py` always returns 0 — **confirmed present**

**File:** `ingest/main.py`, lines 614, 617  
**Class:** C (dishonest exit code).

`_run()` returns `0` unconditionally at both terminal conditions (`--max-tracks`
hit at line 614, queue drained at line 617), regardless of
`stats.failed_download`. A run where every download fails logs errors and
returns exit 0 — CI, cron, or a calling script cannot distinguish success from
complete failure. The fix pattern already exists in `loop_hardening.exit_status()`:

```python
# current
return 0

# fix
from scripts.loop_hardening import exit_status
return exit_status(stats.downloaded, stats.failed_download)
```

Graded MEDIUM rather than HIGH because `ingest/main.py` is not long-running
(downloads are bounded) and failures are logged prominently, but the dishonest
exit propagates to any automated caller.

### 3.3 MEDIUM (carried) · C1+C3 — `gpu_worker.py` `n_done`/`return 0` — **confirmed present**

**File:** `analysis/gpu_worker.py`, lines ~364, 369, 372  
**Class:** C (silent-failure loop) — C3 honest-counting + C1 honest exit code.

`n_done` is incremented on both success and failure paths; both terminal returns
are `return 0` with no call to `exit_status(n_done, n_failed)`. A GPU box session
where every track fails returns exit 0 and writes no records. `--max-tracks N`
exhausted by consecutive failures terminates without a single successful write,
but the caller sees exit 0. Carried from 2026-07-27 audit.

### 3.5 LOW (new) · B — `rsync_stems_out` no `--checksum` and no post-push integrity check — **latent**

**File:** `scripts/mac_analyze_loop.py`, function `rsync_stems_out`  
**Class:** B (no integrity check).  
**Status:** latent.

Outbound stem rsync uses `-aq --timeout` but no `--checksum` and no remote
sha256 comparison. The inbound `rsync_in` path is fully guarded (sha256 verified).
Asymmetry: stems are regenerable from source audio, so a truncated push would
be silently accepted and stem analysis re-triggered on the next loop. Low severity
given regenerability. Analogous to the prior LOW-B sha256 `OSError` finding (3.2).

### 3.6 LOW (carried) · B — `mac_analyze_loop.py:~454` sha256_file missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py`, lines ~454–463  
**Class:** B (latent B-class gap).  
**Status:** latent.

`sha256_file(local_audio)` is called without a `try/except OSError`. An unreadable
file would propagate uncaught, killing the analysis thread for that track without
calling `persist_failed_inc()`. `set_mert_backfill_loop.py` (now absent) had the
guard; `mac_analyze_loop.py` still does not.
