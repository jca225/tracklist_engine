### Class A — Encoding / Mojibake

#### A1 · HIGH · confirmed present
**`ingest/adapters/spotdl_adapter.py` lines 99, 232 — `text=True` without `encoding=` in spotdl subprocess calls**

Both `download_one` and `download_batch` call `subprocess.run(..., capture_output=True, text=True, timeout=...)` with no `encoding=`. On pi-storage (documented Latin-1 locale), a non-ASCII character in spotdl stderr output (e.g. "Beyoncé – Halo not found") can produce a `UnicodeDecodeError` that propagates uncaught past the `except (subprocess.TimeoutExpired, OSError)` guards in both callers, crashing the entire per-track or per-batch iteration. Even when not UnicodeDecodeError, the text is latin-1-decoded mojibake that breaks `"not found" in msg.lower()` keyword matching used for `unavailable` classification.

`loop_hardening.TEXT_KW` = `{"text": True, "encoding": "utf-8", "errors": "surrogateescape"}` was introduced for this exact boundary; `spotdl_adapter.py` pre-dates it and was not updated.

**Fix:** add `encoding="utf-8", errors="surrogateescape"` to both subprocess.run calls.

### Class B — Missing Timeout / Integrity Check

#### B1 · MEDIUM · latent/hardening
**`mac_analyze_loop.py` `rsync_stems_out` (line 191) — no post-push integrity check**

Stems are pushed to pi-storage with `rsync -aq` (no `--checksum`) and no post-push sha256 verification. A torn or silent network failure that rsync does not detect leaves corrupt stems on pi-storage while the DB rows point to them. `loop_hardening.sha256_file` exists for this purpose but is not called on the push side.

**Grade:** Medium/latent — only manifests on rsync data corruption, not on clean connections.

#### B2 · LOW · latent/hardening
**`mac_analyze_loop.py` `rsync_in` (lines 171–188) — post-pull sha256 check conditional on asset.sha256 being non-null**

The sha256 integrity check at lines 454–456 is guarded by `if asset.sha256:`. Tracks ingested without a stored sha256 (older rows, manually-ingested files) proceed directly to 200–250 s of MPS analysis with no integrity verification. A truncated pull produces corrupt analysis rows in canonical.

**Grade:** Low/latent — requires a truncated pull AND a missing sha256 in the DB.

### Class C — Silent Failure / Dishonest Exit Code

#### C1 · HIGH · confirmed present
**`mac_analyze_loop.py` lines 419, 517 — `except subprocess.CalledProcessError` misses `TimeoutExpired` in both bg-persist thread and main loop**

`subprocess.TimeoutExpired` is a subclass of `subprocess.SubprocessError`, **not** of `CalledProcessError`. The two catch sites use the narrower type.

**Main loop (line 517):** A timeout on rsync or ssh in the pull phase raises `TimeoutExpired`, escapes the `except CalledProcessError` handler, and crashes the entire main loop with an unhandled traceback. The transient retry logic from `loop_hardening.register_transient` — specifically designed for timeout/hang — is bypassed for the most common transient failure class.

**`_persist_in_bg` (line 419):** The background persist thread catches only `CalledProcessError`. Any `TimeoutExpired` (e.g. the 120s `subprocess.check_output` of the local sqlite3 dump at line 302) or `sqlite3.OperationalError` (e.g. scratch DB corruption) escapes silently. Consequences:
- `counts.persist_failed_inc()` is never called → the failed track is invisible to `exit_status`.
- The track's id is never added to `failed_tids` → `next_task()` returns the same track on every subsequent iteration → **infinite silent poison-pill re-analysis** (200–250 s of MPS time per cycle).
- When eventually drained (e.g. after human intervention), `exit_status(n_done=0, n_failed=0, n_persist_failed=0)` returns **exit 0** + INFO "queue drained — analyzed 0, failed 0" — a cheerful success report for a run where every bg push silently exploded. This directly contradicts the C1 design intent in `loop_hardening.py`.

**Fix:** change both except clauses to `except subprocess.SubprocessError` (covers both CalledProcessError and TimeoutExpired). Add a separate `except (sqlite3.DatabaseError, OSError)` for the bg thread body.

#### C2 · HIGH · confirmed present
**`replace_track_audio.py` line 654 — `except (subprocess.SubprocessError, ValueError)` misses `OSError` in `_probe_duration_s`**

`subprocess.SubprocessError` does not cover `OSError`. If ffprobe is installed but returns an `OSError` subclass at execution time (e.g., `ETXTBSY`, bad ELF architecture, or another exec failure mode beyond PermissionError, which shutil.which already guards), the exception propagates unhandled through `_duration_gate` → `_insert_and_report` → the calling `_replace_via_*` function → `_run`, crashing the script after the new audio file has already been placed on disk but before any DB insert. The old row is left intact (INSERT-before-DELETE semantics protect it), so data integrity is preserved — but the script exits nonzero with an unhandled traceback rather than a clean error message.

**Fix:** change the except to `except (subprocess.SubprocessError, ValueError, OSError)`.

#### C3 · MEDIUM · confirmed present
**`ingest/main.py` line 617 + `ingest/main_retry.py` line 417 — both `_run()` functions return 0 unconditionally**

Neither file applies `loop_hardening.exit_status` or equivalent. A run where all 300 candidates timed out, or where the DB was failing mid-pass, exits 0. Monitoring (systemd `SuccessExitStatus`, CI, alerting) cannot distinguish clean from wholesale failure.

`ingest/main.py` has the additional gap that `db_failed` occurrences (lines 608–609, 523–531) are logged at ERROR but have no `RunStats` field and do not influence the exit code. A disk-full event on pi-storage mid-run presents only as a low `downloaded` count in the DONE summary line.

**Fix:** add nonzero exit when `stats.failed / stats.candidates > threshold` or `stats.db_failed > 0`; add `db_failed: int = 0` to `RunStats` in `ingest/main.py`.

#### C4 · MEDIUM · confirmed present
**`replace_track_audio.py` line 275 — unguarded `p.unlink()` after a committed `DELETE`**

In `_delete_old_row_if_exists`, the DB DELETE is committed at line 271 before `p.unlink()` at line 275. Any `PermissionError`, `OSError`, or `IsADirectoryError` from the unlink propagates out of the function, through `_insert_and_report`, and crashes the replace script with an unhandled traceback **after** the old row is already gone from the DB and the new row is already committed. The caller's nonzero exit is honest, but the state left behind is inconsistent: the old audio file is orphaned on disk with no DB row referencing it.

**Fix:** wrap `p.unlink()` in `try/except OSError` with an `_log.warning`; the DELETE already achieved the intent.

#### C5 · MEDIUM · latent/hardening
**`ingest/main_retry.py` line 256 — batch-timeout formula can produce hour-scale stalls**

`batch_timeout = max(args.timeout * 2, (bs / threads) * args.timeout * 2)`. With `--batch-size=100 --threads=1 --timeout=60`, this yields 12,000 s (3.3 h). If spotdl hangs at OAuth auth before processing any track in the batch (rather than per-URL), all 99 remaining items wait the full 3.3 hours before a timeout fires. The default `--batch-size=1` is safe; the documented guidance for a tier-1 corpus pass ("10-20") at `--threads=1` is not.

**Grade:** Medium/latent — only triggered with non-default `--batch-size > 1` and `--threads=1`.

#### C6 · MEDIUM · latent/hardening
**`acquire_variant.py` lines 219–241 — content gate silently skipped when `_lookup_latest_audio_row` returns None**

After `_replace_via_url/file` returns 0 (success), `canonical_ingest` calls `_lookup_latest_audio_row` to target the just-inserted row for the content gate. If the lookup returns `None` (race with another deleter, or an unexpected insert anomaly), `cv` is set to `None` and the content gate is bypassed entirely with no log message. The function returns 0 (success), so the caller has no signal that post-insert verification was skipped.

**Grade:** Medium/latent — requires a race or insert anomaly that leaves no row visible immediately after commit.

### Low findings

#### L1
**`mac_analyze_loop.py` lines 322–328 — scratch-DB DELETE failure after successful canonical push suppresses `counts.done_inc()`**

If `conn.execute(f"DELETE FROM {t} WHERE ...")` raises `sqlite3.DatabaseError` during the scratch cleanup at lines 322–328, the exception propagates out of `push_track_rows`, past `except CalledProcessError` in `_persist_in_bg` (uncaught), and the thread dies silently. `counts.done_inc()` (line 417, after `push_track_rows()` returns) is never called. The canonical push already succeeded, but the track is counted neither done nor failed.

**Grade:** Low — requires local scratch DB corruption, which would surface through other symptoms.

#### L2
**`mac_analyze_loop.py` line 109 — `_set_filter_clause` builds unparameterized SQL from `--set-ids` CLI argument**

`ids` values are wrapped in single quotes (`f"'{s}'"`) but not parameterized. Values containing embedded single quotes could break the SQL. The injection path requires a user who controls the `--set-ids` flag and crafts a value that survives both single-quote wrapping and the remote shell double-quote wrapper in `ssh_pi`. Low practical risk for a single-user CLI tool.

#### L3
**`acquire_variant.py` line 97 — provenance TSV opened without `encoding=utf-8`**

`log.open("a")` with no encoding. On a Latin-1 host, non-ASCII track names in `--name` write mojibake bytes into `replacements.tsv`. Not data-loss, but inconsistent with `loop_hardening.TEXT_KW`.

#### L4
**`replace_track_audio.py` line 650 — `text=True` without `encoding=` in ffprobe subprocess call**

ffprobe output for `format=duration` is pure ASCII decimal, so no UnicodeDecodeError in practice, but it deviates from the project's `TEXT_KW` discipline. On a Latin-1 locale `getpreferredencoding()` decodes correctly for ASCII anyway.

#### L5
**`replace_track_audio.py` lines 279–280 — false-positive "deleted old stems dir" log when `rmtree(ignore_errors=True)` silently failed**

The log line fires unconditionally after `shutil.rmtree(stems_dir, ignore_errors=True)`. If rmtree suppressed an error (permissions, NFS lock), the log still reads "deleted old stems dir", masking that orphaned stems remain on disk.

#### L6
**`analysis/persistence.py` line 83 — `.decode()` without encoding on `git rev-parse` output**

`subprocess.check_output(...).decode().strip()` with no encoding argument. Git SHAs are pure ASCII so this will never misfire, but the outer `except Exception` catches and swallows a hypothetical error anyway. Pure style deviation.
