## 3. Carried open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` always exits 0, `n_done` incremented on failure

**File:** `analysis/gpu_worker.py` · Lines ~355–373  
**Status:** Confirmed still present on main.

`n_done` is incremented on both success and failure paths in `--loop` mode:

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← failure advances the counter (C3 honest-count miss)
    continue
_log.info("OK [%d] ...", n_done + 1, ...)
n_done += 1
```

Both exit sites return 0 unconditionally (`return 0` after queue-drain; `return 0`
after `--max-tracks` hit) with no call to `loop_hardening.exit_status()`.

Consequences:
1. An all-failure run logs a cheerful INFO "done" and exits 0 — a systemd/cron
   supervisor treats it as success.
2. `--max-tracks N` is consumed by failures: 10 consecutive failures with
   `--max-tracks=10` terminates without writing a single row, yet exits 0.

`mac_analyze_loop.py` already imports and uses `loop_hardening.exit_status()` as
the correct pattern. Fix: rename the failure-path increment to a separate
`n_failed` counter; call `exit_status(n_done, n_failed)` at both terminal sites.

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

```python
if asset.sha256:

```

without calling `persist_failed_inc()`, undercounting failures.

### 3.3 LOW (carried) · C3 — `mac_analyze_loop._persist_in_bg` catches only `CalledProcessError`

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424

`_persist_in_bg` only catches `subprocess.CalledProcessError`. An `OSError`
(scratch DB path missing) or `sqlite3.OperationalError` (lock timeout on scratch
write) would terminate the background thread silently without calling
`persist_failed_inc()` — the `Counts` tally would undercount failures.
