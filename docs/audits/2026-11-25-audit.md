## 3. Open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` loop increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~359–372

**Class:** C — C3 honest-counting + C1 honest exit code. Status: **confirmed present**.

`n_done` is incremented on both success and failure paths, and both terminal
conditions (`queue drained`, `--max-tracks` hit) unconditionally `return 0`:

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1      # ← C3: done counter advanced on failure
    continue
_log.info("OK [%d] ...", n_done + 1, ...)
n_done += 1
...
_log.info("hit --max-tracks=%d, stopping", args.max_tracks)
return 0             # ← C1: always exits 0 regardless of failure ratio
```

Consequences:
1. A run where every track fails logs "done" and returns exit 0 — CI/cron
   treats it as success. Compare: `mac_analyze_loop.py` calls
   `exit_status(n_done, n_failed)` which escalates to nonzero+ERROR when
   `n_done == 0` or the failure ratio exceeds the threshold.
2. `--max-tracks N` is driven by `n_done`. Ten consecutive failures with
   `--max-tracks=10` exhaust the limit without producing any records; the
   caller receives exit 0.

**Recommended fix:** track a separate `n_failed` counter; increment it (not
`n_done`) on failure; call `loop_hardening.exit_status(n_done, n_failed)` at
both return sites instead of `return 0`. This matches the contract already used
by `mac_analyze_loop.py`.

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

**Class:** B — missing integrity-check guard. Status: **confirmed present (latent)**.

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

An `OSError` here would propagate uncaught through the main loop's `try` block,
landing in the `CalledProcessError` handler and triggering `register_transient`
— which is misleading (it's a local file I/O error, not a network/SSH failure)
and would wastefully retry instead of quarantining. Impact: low (rsync would
have to succeed and then the file become unreadable in the same window), but the
inconsistency with `loop_hardening`'s design intent is worth fixing.
