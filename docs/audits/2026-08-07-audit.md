### 2.3 Class C — Silent-failure loops

#### MEDIUM (carried) · C1+C3 — `gpu_worker.py` loop mode: `n_done` counts failures, exits 0 on all-fail

**File:** `analysis/gpu_worker.py` · Lines 326–372  
**Status:** Confirmed present — unfixed since 2026-07-27

`n_done` is incremented on both success (line 369) and failure (line 364), so
`--max-tracks N` counts N *attempts* rather than N *successes*. Both loop
exit-points return `0`: queue drain ("no unanalyzed tracks remain", line 337)
and `--max-tracks` exhaustion (line 371). No `exit_status()` call from
`loop_hardening` is made.

Consequence: a GPU box run where every track is a poison-pill that fails and
quarantines into `failed_tids` drains the queue via `_next_unanalyzed →
None` and exits 0. Monitoring, CI, and `gpubox`'s success-checking layer all
read it as a clean run.

Compare: `mac_analyze_loop.py` calls `exit_status(done, failed, pf)` at the
drain point, returning nonzero + ERROR when `n_done == 0` or failure ratio
exceeds 50%.

**Fix:** separate `n_failed` counter; call `loop_hardening.exit_status(n_done,
n_failed)` at both return sites.

#### MEDIUM (carried, refined) · C3 — `mac_analyze_loop._persist_in_bg`: multiple exception classes escape

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424  
**Status:** Carried from prior audits. This run confirms an additional escape
path vs. the documented `TimeoutExpired` gap.

```python
def _persist_in_bg(tid: int, stem_local: Path) -> None:
    try:
        ...
        push_track_rows(tid)
        counts.done_inc()
    except subprocess.CalledProcessError as e:   # ← only this is caught
        counts.persist_failed_inc()
        log.error(...)
    finally:
        ...
```

`push_track_rows` contains raw `_sqlite3.connect(SCRATCH_DB)` / `.execute()` /
`.commit()` calls (mac_analyze_loop.py lines 242, 261, 324) that can raise
`sqlite3.OperationalError` or `sqlite3.DatabaseError`. These are sibling
exception classes (not subclasses of `CalledProcessError`) and escape the
handler. Python's threading layer swallows the unhandled exception silently;
both `counts.done_inc()` and `counts.persist_failed_inc()` are skipped. The
honest-count guarantee (C3) is violated: `exit_status()` receives a
`n_persist_failed` it cannot trust. The track re-enters the queue on the next
`next_task()` call (no `track_analysis` row written), so data is not lost, but
the session count diverges.

Separately confirmed (2026-08-03 upgrade): `subprocess.TimeoutExpired` is also
not a subclass of `CalledProcessError` and escapes when `RSYNC_TIMEOUT` or
`SSH_PUSH_TIMEOUT` fires inside the bg thread.

**Fix:** Widen to `except (subprocess.CalledProcessError,
subprocess.TimeoutExpired, sqlite3.Error) as e:` — or use `except Exception`
with `log.exception` to future-proof against other bg-thread failures.

### 2.4 Intentional-design notes (not findings)

**`ingest/main.py` and `ingest/main_retry.py` always return 0.** Already
tracked as HIGH/MEDIUM in issue #8. These are resilient best-effort batch
pipelines where per-download failures are logged and expected; the always-0
exit is a design choice. The prior audit's grading (HIGH for main.py) stands
for monitoring purposes but is noted here as design-documented rather than
accidental.

**`ingest/adapters/spotdl_adapter.download_batch()`:** The staging temp-dir
creation (`tempfile.mkdtemp`) is unguarded against races in a concurrent
process environment, but `download_batch` is called sequentially by
`main_retry._run_batched`, so there is no practical concurrency exposure.
