## 3. Open findings

### 3.1 MEDIUM (new) · C1 — `ingest/main_retry.py` always returns 0

**File:** `ingest/main_retry.py` · Line 417

**Class:** C (dishonest exit code).

The `_run` function's terminal `return 0` fires regardless of `stats.db_failed`:

```python
_log.info(
    "DONE | candidates=%d downloaded=%d timeout=%d gone=%d other=%d db=%d in %.0fs",
    stats.candidates, stats.downloaded, stats.failed_timeout,
    stats.failed_unavailable, stats.failed_other, stats.db_failed, elapsed,
)
return 0   # ← always 0, even when stats.db_failed > 0
```

`timeout` and `unavailable` failures are expected outcomes for a targeted retry
pass — no bug. But `db_failed` is a genuine error class (DB insert failed after
a successful download). A monitoring wrapper or CI job checking the exit code
cannot distinguish a fully-successful run from one where all downloads failed to
persist. Compare: `gpu_worker.py` finding 3.2 (carried below) and
`mac_analyze_loop.py` which calls `exit_status()` from `loop_hardening`.

**Fix:** `return 1 if stats.db_failed else 0` at line 417, or import and call
`exit_status(stats.downloaded, stats.db_failed)[0]` for the same contract as the
other loops.

Grade: **Medium** (manual/occasional tool, not a hot loop; failures are
log-visible; but db_failed is a real error class distinct from expected
unavailables).

### 3.2 MEDIUM (carried) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~359–372

Carried from 2026-07-27 audit (finding 3.1, priority #1). **Not fixed.**

`n_done` is incremented on both success and failure paths:

```python
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: done counter advanced on failure
    continue
_log.info("OK [%d] ...", n_done + 1, ...)
n_done += 1
```

The loop exits via `return 0` at both terminal conditions (queue drained and
`--max-tracks` hit) without calling `exit_status()`. A session where every
track fails returns exit 0 and logs nothing. `--max-tracks N` is exhausted by
failures, not successes.

**Fix (same as prior audit):** track `n_failed` separately; call
`loop_hardening.exit_status(n_done, n_failed)` at both return sites.

### 3.3 LOW (carried) · B — `mac_analyze_loop.py:454` sha256_file missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

Carried from 2026-07-27 audit (finding 3.2). **Not fixed.**

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

An `OSError` here would propagate uncaught into the hot path, killing analysis
for that track without calling `persist_failed_inc()`. `set_mert_backfill_loop`
had the guard (now removed with that file); the inconsistency remains in the
mac loop.

**Fix (one-liner):** wrap in `try/except OSError`; on failure treat as transient
via `register_transient`.

### 3.4 LOW (carried) · C3 — `mac_analyze_loop.py _persist_in_bg` narrow exception scope

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424

Carried from 2026-07-27 audit (finding 3.4). **Not fixed.**

`_persist_in_bg` only catches `subprocess.CalledProcessError`. An `OSError`
(scratch DB path missing) or `sqlite3.OperationalError` (lock timeout) would
terminate the background thread silently without calling `persist_failed_inc()`
— Counts tally underreports failures.

**Fix:** widen the except clause to `(subprocess.CalledProcessError, OSError,
sqlite3.OperationalError)` or use a broad `Exception` with a re-raise on
`KeyboardInterrupt`.
