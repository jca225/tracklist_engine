## 3. Open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~364–372

Originally reported 2026-07-27 (finding 3.1). **Still present.**

`n_done` is incremented on the analysis-fail path and at the `--max-tracks`
drain, and the function returns `0` unconditionally at both terminal conditions.
Consequences: (1) a session where every track fails reports `0` — CI/cron treats
it as success; (2) `--max-tracks=N` can be exhausted entirely by failures without
a single successful analysis.

**Fix:** increment a separate `n_failed` counter on the failure path; call
`exit_status(n_done, n_failed)` from `loop_hardening` instead of `return 0`.

### 3.2 MEDIUM (new) · C1 — `ingest/main_retry.py` always returns exit code 0

**File:** `ingest/main_retry.py` · Line ~417

`_run()` ends unconditionally with `return 0`. A full-corpus Spotify retry pass
where every download times out or is unavailable still exits `0` — the operator
or cron job has no signal from the exit code that all work failed.

```python
    _log.info("DONE | candidates=%d downloaded=%d timeout=%d ...", ...)
    return 0        # ← always 0, regardless of downloaded count
```

Unlike the analysis loops (`mac_analyze_loop.py`, `gpu_worker.py`), this script
does not import or call `exit_status()` from `loop_hardening`. `loop_hardening`
already exports exactly the right primitive.

**Fix:** call `exit_status(stats.downloaded, stats.failed_timeout + stats.failed_other + stats.db_failed)` and use the returned `(code, level, msg)` tuple for the final log + return.

**Grade:** confirmed present.

### 3.3 MEDIUM (new) · B1 — `ingest/adapters/downloader.py` yt-dlp API calls lack `socket_timeout`

**File:** `ingest/adapters/downloader.py` · Lines ~50–74 (`_ydl_opts`)

`_ydl_opts()` configures retries but no `socket_timeout`:

```python
opts: dict = {
    "format": "bestaudio/best",
    "retries": cfg.retries,
    "postprocessors": [...],
    # no socket_timeout
}
```

`YoutubeDL.extract_info()` is a Python API call (not a subprocess), so it falls
outside `loop_hardening`'s subprocess timeout constants. Python's socket defaults
are blocking/infinite unless `socket.setdefaulttimeout()` is set. If a YouTube
or SoundCloud TCP connection stalls at the OS level (no EOF, no RST), the call
hangs indefinitely — blocking `ingest.main` for the lifetime of the OS TCP
keepalive timer (minutes to hours depending on the machine).

This affects both `download_one` (line ~105) and `download_set_mix` (line ~163).

**Fix:** add `"socket_timeout": 60` (or similar) to `_ydl_opts`. yt-dlp respects
this key natively.

**Grade:** latent (requires a stalled TCP connection; normal failures raise
`YtDlpDownloadError` promptly). Operationally real on pi-storage over
Tailscale during Vast reboots.

### 3.4 LOW (carried) · C3 — `mac_analyze_loop.py:_persist_in_bg` exception scope too narrow

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424

Originally reported 2026-07-27 (finding 3.4). **Still present.** Prior report
noted `OSError` / `sqlite3.OperationalError`; this run adds a third uncaught
class: `subprocess.TimeoutExpired`.

```python
except subprocess.CalledProcessError as e:   # ← TimeoutExpired is a sibling, NOT caught
    counts.persist_failed_inc()
```

`rsync_stems_out` and `push_track_rows` both call `subprocess.check_call` / `subprocess.run`
with `timeout=RSYNC_TIMEOUT` (600 s) and `timeout=SSH_PUSH_TIMEOUT` (300 s).
If those timeouts fire, `TimeoutExpired` propagates uncaught through the
background thread. `counts.persist_failed` is not incremented, the thread
terminates via `threading.excepthook` (stderr only, not the module logger), and
`exit_status()` sees an under-count of failures.

Correctness impact: the track is not committed to canonical, so `next_task`
re-picks it on the next loop iteration (no data loss). Accounting impact: the
exit code may be 0 when it should be nonzero.

**Fix:** widen to `except subprocess.SubprocessError` (covers both
`CalledProcessError` and `TimeoutExpired`). Add `OSError` to be complete.

### 3.5 LOW (new) · B1 — `mac_analyze_loop.py` main loop misses `TimeoutExpired` from `rsync_in`

**File:** `scripts/mac_analyze_loop.py` · Lines ~445–523

The main `while True:` try-block catches `subprocess.CalledProcessError` (line
~517) but not `subprocess.TimeoutExpired`:

```python
    try:
        rsync_in(remote_path, local_audio)       # ← subprocess.check_call with timeout=RSYNC_TIMEOUT
        ...
    except subprocess.CalledProcessError as e:   # TimeoutExpired is NOT caught here
        register_transient(...)
    finally:
        local_audio.unlink()
```

If rsync makes continuous progress but the total wall-clock exceeds
`RSYNC_TIMEOUT=600 s` (very large file or very slow Tailscale link), the main
loop process dies rather than retrying via `register_transient`.

In practice this is unlikely: rsync's own `--timeout=RSYNC_IO_TIMEOUT=300 s`
exits non-zero (→ `CalledProcessError`) on any 300 s I/O stall, which handles
the dominant failure mode. The residual risk is a very slow but never-stalling
transfer on a large file.

**Fix:** widen to `except subprocess.SubprocessError` at line ~517 alongside the
`_persist_in_bg` fix (finding 3.4).
