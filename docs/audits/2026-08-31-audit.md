## 3. New findings

### 3.1 MEDIUM · A — `spotdl_adapter.py`: `text=True` without explicit encoding

**File:** `ingest/adapters/spotdl_adapter.py` · Lines 99, 232

**Class:** A (mojibake at subprocess boundary)

Both the per-track sequential path and the batch path call spotdl via:

```python
proc = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout_s)
```

No `encoding=` is specified. Python falls back to `locale.getpreferredencoding(False)`.
On systems where the locale is `C` or `POSIX` (ASCII), or Latin-1, decoding
spotdl's stdout/stderr will either raise `UnicodeDecodeError` or silently
produce mojibake. spotdl outputs artist and track names in its progress log —
international music with non-ASCII characters (very common in DJ sets) is the trigger.

The `net_subprocess_no_encoding` entropy fence counts this (current: 8 vs
baseline 25) but the instances in this file have not been fixed. Unlike the
SSH/rsync paths covered by `loop_hardening.TEXT_KW`, these are spotdl-specific
and not covered by the centralised hardening module.

After a `UnicodeDecodeError`, `proc.stderr` / `proc.stdout` are unavailable,
so the heuristic `"not found" in msg.lower()` at line 110 / 237 cannot run and
the exception propagates out of `download_one` / `download_batch` uncaught —
crashing the caller (`_attempt` / `_run_batched`).

**Grade:** Medium · latent (locale is UTF-8 on most modern Linux; risk rises
on minimal containers or older pi-storage locales)

**Fix:** Add `encoding="utf-8", errors="surrogateescape"` at both call sites
(same pattern as `loop_hardening.TEXT_KW`):

```python
proc = subprocess.run(
    cmd, capture_output=True, text=True,
    encoding="utf-8", errors="surrogateescape",
    timeout=timeout_s,
)
```
