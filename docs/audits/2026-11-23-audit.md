## 3. Open findings

### 3.1 HIGH (carried from 2026-11-18) · C — `mac_analyze_loop._persist_in_bg` narrow except

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424

**Class:** C (silent-failure) — exception scope too narrow.

`_persist_in_bg` calls `push_track_rows`, which makes direct
`sqlite3.connect(SCRATCH_DB)` calls (lines 230, 242, 261, 324). Those calls
raise `sqlite3.OperationalError` or `sqlite3.DatabaseError` on lock contention,
corruption, or a missing path. The except clause at line 419 catches only
`subprocess.CalledProcessError`:

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

An uncaught `sqlite3.OperationalError` kills the background thread silently.
`counts.done_inc()` is never called (correct) but neither is
`counts.persist_failed_inc()` — `exit_status()` sees neither a success nor a
failure, so a session with a broken scratch DB drains and exits 0 with zero rows
written.

**Fix:** `except (subprocess.CalledProcessError, sqlite3.Error, OSError) as e:`
and call `persist_failed_inc()` in the handler. Same fix as the 2026-11-18
report.

### 3.2 MEDIUM (carried from 2026-11-18) · C — `ingest/main.py` always returns exit 0

**File:** `ingest/main.py` · Lines 614, 617

**Class:** C (dishonest exit code, C1).

`_run()` returns `0` unconditionally at both terminal points:

```python
if args.max_tracks is not None and stats.downloaded >= args.max_tracks:
    ...
    return 0   # line 614

_summarize(stats, time.monotonic() - t0)
return 0       # line 617
```

`stats.failed_download` is tracked and logged but never influences the exit
code. A corpus run where every download fails (e.g. yt-dlp bot-detected) logs
errors and returns 0. CI/cron cannot distinguish full success from complete
failure.

**Fix:** apply `loop_hardening.exit_status(stats.downloaded, stats.failed_download)`
(already used by `mac_analyze_loop.py`).

### 3.3 MEDIUM (carried from 2026-07-27) · C — `gpu_worker.py` `n_done` on failure path, `return 0`

**File:** `analysis/gpu_worker.py` · Lines ~364, 369, 372

**Class:** C (dishonest counting C3 + dishonest exit code C1).

`n_done` is incremented on both the success path (line 369) and the failure
path (line 364), so `--max-tracks N` with N consecutive failures exhausts the
limit without a single successful analysis. Both terminal returns are
`return 0` with no `exit_status()` call. A session where every track fails
returns exit 0 and logs nothing alarming.

Compare: `mac_analyze_loop.py` calls `exit_status(n_done, n_failed)`, which
escalates when `n_done == 0` or when the failure ratio exceeds 50%.

**Fix:**
- Increment `n_failed` (not `n_done`) on the failure path.
- Call `exit_status(n_done, n_failed)` at both terminal returns instead of
  `return 0`.

### 3.4 LOW (new) · C — `ingest/main_retry.py` always returns exit 0

**File:** `ingest/main_retry.py` · Line 417

**Class:** C1 (dishonest exit code), latent.

`_run()` always returns `0` regardless of `stats.failed_timeout`,
`stats.failed_other`, or `stats.db_failed`. If the script times out on all
candidates (174 consecutive timeouts were observed in the founding run), it
still exits 0. The exit code matters only if the script is wired into cron
alerting — it is typically run interactively or as a one-shot parallelized
pass, so severity is low.

**Note:** `main_retry.py` was in scope in the 2026-07-27 and 2026-11-18 audits;
no finding was recorded then. Surfaced now.

**Fix:** follow the same `exit_status(downloaded, failed)` pattern; at minimum,
return 1 when `stats.downloaded == 0` and candidates existed.
