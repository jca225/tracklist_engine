## 3. Findings

### 3.1 BLOCKER · C — `mac_analyze_loop.py` `next_task()` outside try/except **[NEW]**

**File:** `scripts/mac_analyze_loop.py` · Line 431

**Class:** C (silent-failure loop)

`next_task()` at line 431 is called OUTSIDE the `try:` block (which begins at line
445). `next_task` calls `ssh_pi`, which can raise `subprocess.CalledProcessError`
(SSH auth failure, remote error) or `subprocess.TimeoutExpired` (120s limit).
Neither is caught — the exception propagates unhandled and kills the entire
multi-hour analysis loop on the first queue-poll failure. The transient-retry path
(`register_transient` + backoff) at line 517 is structurally unreachable for this
call site.

**Scenario:** Tailscale blip during `next_task` → `TimeoutExpired` on `ssh_pi` →
loop exits with unhandled exception after whatever tracks were queued, dropping the
rest of a corpus batch silently.

**Fix:** Either fold `next_task(...)` inside the existing `try:` block (line 445),
or wrap it in a separate `try/except (subprocess.CalledProcessError,
subprocess.TimeoutExpired)` that routes to `register_transient`.

### 3.2 HIGH · C — `mac_analyze_loop.py` `_persist_in_bg` missing `TimeoutExpired` **[NEW, deepened from LOW 2026-07-27]**

**File:** `scripts/mac_analyze_loop.py` · Lines 409–421

**Class:** C (counting invariant broken)

`_persist_in_bg` at line 419 catches only `subprocess.CalledProcessError`.
Both `rsync_stems_out` and `push_track_rows` inside the try block are called with
explicit `timeout=` arguments (RSYNC_TIMEOUT / SSH_PUSH_TIMEOUT). When a timeout
fires, `TimeoutExpired` is raised, escapes the handler, and the thread exits with
an unhandled exception. Neither `counts.done_inc()` nor `counts.persist_failed_inc()`
is called. `exit_status()` at loop exit receives incorrect inputs — failure ratio
and persist-failed check both undercount. A run where all persist threads time out
can exit 0 with a dishonest INFO message.

**Fix:** Change line 419 to
`except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:`.

### 3.3 HIGH (latent) · B — `ingest/adapters/downloader.py` missing `socket_timeout` **[NEW]**

**File:** `ingest/adapters/downloader.py` · Lines 50–74

**Class:** B (missing wall-clock timeout)

`_ydl_opts` configures `retries=3` (attempt count) but omits `socket_timeout`
(per-operation socket deadline). yt-dlp's `socket_timeout` gates connection setup
but not an ongoing stalled transfer. A download where bytes arrive at even 1 B/s
never triggers it, leaving the yt-dlp process hung indefinitely. For mix-file
downloads (`download_set_mix` — files can be 1 GB+) this is a real hang
vector: a single stall can block the analysis loop for hours. `loop_hardening`
RSYNC_TIMEOUT / RSYNC_IO_TIMEOUT are the canonical pattern; no equivalent is wired
here.

**Fix:** Add `"socket_timeout": 30` (connection setup) and, more critically,
either invoke yt-dlp as a subprocess with a wall-clock `timeout=` argument
(comparable to RSYNC_TIMEOUT), or add a `progress_hook` that calls
`ydl.params["abort"] = True` if no progress is made for N seconds.

### 3.4 MEDIUM (carried since 2026-07-27) · C1+C3 — `gpu_worker.py` `n_done`/`return 0`

**File:** `analysis/gpu_worker.py` · Lines ~307, 337, 364, 369, 372

`n_done` is incremented on both success and failure paths (line 364 in the failure
branch, line 369 in the success branch). All three return sites use bare `return 0`
without calling `loop_hardening.exit_status()`. A session where every track fails
exits 0. `--max-tracks=N` is consumed by `n_done`, so 10 consecutive failures with
`--max-tracks=10` exhaust the limit without producing any analysis records; the
caller receives exit 0. Unresolved since 2026-07-27.

**Fix:** increment `n_failed` (not `n_done`) on the failure path; call
`exit_status(n_done, n_failed)` at all three return sites.

### 3.5 MEDIUM (carried from 2026-10-09) · C — `mac_analyze_loop.py` main loop misses `TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Line 517

`except subprocess.CalledProcessError` does NOT catch `subprocess.TimeoutExpired`.
When `rsync_in` or `ssh_pi` hit their wall-clock backstop, `TimeoutExpired` escapes
and crashes the loop. In practice SSH keepalives catch most dead links as
`CalledProcessError`, so this fires only on rare stuck-but-alive transfers —
but when it does, the loop is gone rather than retrying. Unresolved since 2026-10-09.

Note: Finding 3.1 (Blocker) is a higher-severity variant of the same root cause
— fix 3.1 first.

### 3.6 MEDIUM (new) · A — `replace_track_audio.py` `UnicodeEncodeError` on Latin-1 stdout **[NEW]**

**File:** `scripts/replace_track_audio.py` · Line 966

**Class:** A (encoding at OS boundary)

`_emit_case_record` calls `print("ACQUISITION_CASE\t" + json.dumps(payload, ensure_ascii=False))` without reconfiguring stdout. On pi-storage with a Latin-1 locale, any non-Latin-1 character in `payload` (CJK track title, non-ASCII URL) raises `UnicodeEncodeError` after the DB and ledger writes have already succeeded, returning exit code 1 via unhandled exception. The sibling scripts `acquire_variant.py` (line 366) and `replace_stem_audio.py` (line 100) both call `stream.reconfigure(errors="replace")` at the top of `_run()` — `replace_track_audio.py` lacks this guard.

**Fix:** Add `stream.reconfigure(errors="replace")` at the top of `_run()` matching the sibling scripts, or change `ensure_ascii=False` → `ensure_ascii=True` on line 966.

### 3.7 MEDIUM (new) · C — `loop_prefetch.py` `_pick()` outside try/except **[NEW]**

**File:** `scripts/loop_prefetch.py` · Line 86

**Class:** C (silent false-completion)

`_run()` calls `self._pick(skip_tids)` at line 86 BEFORE the `try:` block (line
91). If `_pick` (typically `next_task` → `ssh_pi`) raises `CalledProcessError` or
`TimeoutExpired`, the exception is unhandled: `self._result` stays `None` (set at
`start()` line 103), the thread exits, and `take()` returns `None`. The analysis
loop interprets `None` as "queue drained" and calls `exit_status()` with whatever
counts exist — a silent false-completion that drops every unprocessed track.

**Fix:** Wrap `self._pick(skip_tids)` in the existing `except Exception` block, or
pull it inside the `try:` on line 91.

### 3.8 MEDIUM (new) · C1 — `ingest/main.py` always returns 0 **[NEW]**

**File:** `ingest/main.py` · Lines 614, 617

**Class:** C (dishonest exit code)

`_run()` calls `return 0` unconditionally at both terminal points (`--max-tracks`
hit at line 614, and normal drain at line 617). A 16k-track run where every
download fails (`failed_download` saturated, `downloaded == 0`) returns exit 0.
Monitoring or CI that gates on exit code treats it as success.
`loop_hardening.exit_status()` is not imported.

**Fix:** Import and call `exit_status(downloaded, failed_download)` in place of
`return 0`.

---

### 3.9 MEDIUM (new) · C1 — `ingest/main_retry.py` always returns 0 **[NEW]**

**File:** `ingest/main_retry.py` · Line 417

**Class:** C (dishonest exit code)

Same pattern as 3.8: `_run()` returns 0 unconditionally regardless of
`stats.failed_timeout`, `stats.failed_other`, etc. A run where all candidates time
out still exits 0 with an INFO summary.

**Fix:** Import and call `exit_status(stats.downloaded, stats.failed_timeout + stats.failed_other + stats.db_failed)` in place of `return 0`.

### 3.10 MEDIUM (latent) · B — `analysis/gpu_worker.py` `sqlite3.connect` without timeout **[NEW]**

**File:** `analysis/gpu_worker.py` · Lines 159, 205

**Class:** B (missing timeout on possibly-remote DB)

Both `_next_unanalyzed` (line 159) and `_load_audio_asset` (line 205) call raw
`sqlite3.connect(db_path)`. In the production topology the DB is accessed via sshfs
from a gpubox; a stale mount makes `connect()` (or `.fetchone()`) hang indefinitely.
`loop_hardening.SSH_QUERY_TIMEOUT` (120s) exists for this class but is not used.
Additionally, raw `sqlite3.connect` bypasses the `PRAGMA foreign_keys = ON` from
`core.db.connect`.

### 3.11 MEDIUM (latent) · A — `analysis/gpu_worker.py` mojibake paths on read **[NEW]**

**File:** `analysis/gpu_worker.py` · Line 226

**Class:** A (encoding/mojibake)

`_load_audio_asset` constructs `path=str(row[5])` directly from the DB row without
`repair_double_encoded_utf8`. Rows written before the insert-time repair (#74) may
still carry double-encoded paths. A mojibake path fails `Path(asset.path).exists()`
at line 253, causing the worker to quarantine the track permanently as "audio file
missing" rather than attempting a path repair. A read-time repair call would recover
these tracks.

### 3.14 LOW (latent) · A — `ingest/adapters/spotdl_adapter.py` `text=True` without encoding

**File:** `ingest/adapters/spotdl_adapter.py` · Lines 99, 232

Both `subprocess.run` calls use `text=True` without `encoding='utf-8'`. On pi-storage
with a Latin-1 locale, non-ASCII stdout/stderr is decoded with ISO-8859-1. Currently
only error message truncation uses the output (cosmetic garbling), but any future
path-parsing would silently corrupt filenames. `loop_hardening.TEXT_KW` is the fix.
