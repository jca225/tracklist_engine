## 2. New findings (this audit)

### 2.1 MEDIUM (latent) · C2 — `mac_analyze_loop.py` main loop catches `CalledProcessError` but not `TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Line ~517

**Class:** C2 (transient vs poison distinction broken).

The main loop's outer exception handler:

```python
except subprocess.CalledProcessError as e:
    # Pull/ssh failures reaching here are transient (timeout, broken
    # pipe) — retry with backoff before quarantining (C2).
    if register_transient(tid, str(e), attempts, failed_tids, counts, log):
        n_seen += 1
    else:
        time.sleep(transient_backoff_seconds(attempts[tid]))
```

The comment says "timeout, broken pipe", but `subprocess.TimeoutExpired` is
**not** a subclass of `CalledProcessError` and is not caught. `rsync_in()` uses
`subprocess.check_call(..., timeout=RSYNC_TIMEOUT)` and `fetch_asset()` calls
`ssh_pi()` which uses `subprocess.run(..., timeout=SSH_QUERY_TIMEOUT, check=True)`.
If either fires its subprocess wall-clock timeout, the exception propagates
through `while True`, crashing the loop with an unhandled exception instead of
routing to `register_transient`.

In practice rsync's own `--timeout=300` and SSH's `ServerAliveCountMax=3`
(~45 s detection) typically fire as `CalledProcessError` first. The subprocess
timeout is a belt-and-suspenders backstop, so this is latent — but the failure
mode (hard crash vs. graceful C2 retry) is disproportionately bad.

**Fix:** Add `subprocess.TimeoutExpired` to the except clause and route it
through `register_transient` like `CalledProcessError`.

### 2.2 MEDIUM (latent, extends prior 3.4) · C3 — `_persist_in_bg` also silent on `TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424

**Class:** C3 (dishonest counting).

The 2026-07-27 audit (finding 3.4) noted that `_persist_in_bg` catches only
`subprocess.CalledProcessError`, leaving `OSError` and
`sqlite3.OperationalError` unaccounted. This audit confirms the same gap extends
to `subprocess.TimeoutExpired`:

- `rsync_stems_out()` calls `subprocess.check_call(["ssh", ..., "mkdir -p ..."],
  timeout=SSH_QUERY_TIMEOUT)` and `subprocess.check_call(["rsync", ...],
  timeout=RSYNC_TIMEOUT)` — both can raise `TimeoutExpired`.
- `push_track_rows()` calls `subprocess.check_output(["sqlite3", ...],
  timeout=SSH_QUERY_TIMEOUT)` and `subprocess.run(["ssh", ..., f"sqlite3
  {CANONICAL_DB}"], ..., timeout=SSH_PUSH_TIMEOUT)` — both can raise
  `TimeoutExpired`.

If any fire, the bg thread exits without calling `counts.persist_failed_inc()`.
The track's analysis results are lost to canonical and the exit headline is
wrong.

**Fix:** Widen the `except` clause in `_persist_in_bg` to catch both
`subprocess.CalledProcessError` and `subprocess.TimeoutExpired` (can be a
single `except (subprocess.CalledProcessError, subprocess.TimeoutExpired)`).

## 3. Carried findings (unchanged from 2026-07-27)

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~358–372

`n_done` is incremented on the failure path (line 364) and the loop exits via
`return 0` at all terminal conditions — never calling `exit_status()`. A session
where every track fails still exits 0 and logs "done". Also, `--max-tracks N`
is consumed by `n_done` on failures, so 10 consecutive failures with
`--max-tracks=10` exhaust the limit with zero records written and exit 0.

**Fix:** increment `n_failed` on failure path, call `exit_status(n_done,
n_failed)` at both return sites.

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` sha256_file call missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

`sha256_file(local_audio)` not wrapped in `try/except OSError`. Inconsistent
with the guarded pattern in `set_mert_backfill_loop.py`. If rsync exits 0 and
the file is then unreadable (e.g. NFS race), this would propagate uncaught and
bypass `register_transient`.

### 3.3 LOW (carried) · C2 — backfill loops quarantine on first `CalledProcessError`, no bounded retry

**Files:** `scripts/mert_backfill_loop.py`, `scripts/set_mert_backfill_loop.py`

Neither uses `register_transient` from `loop_hardening`. A transient network
blip causes immediate quarantine for the session.

### 3.4 LOW (carried) · B — `set_mert_backfill_loop.push_set_mert_rows` split transaction

**File:** `scripts/set_mert_backfill_loop.py` · Lines ~193–254

`set_mert_measures` INSERT and `set_analysis.analyzer_versions_json` UPDATE are
in two separate SSH transactions. If the second fails, measure rows exist but
version metadata is stale (won't re-queue due to the `dim=1024` guard, so the
stale version is permanent).
