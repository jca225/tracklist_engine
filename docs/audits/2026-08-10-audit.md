## 3. Open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~359–372  
**Class:** C (silent-failure loop) — C3 honest counting + C1 honest exit code.  
**Status:** Confirmed present (unchanged since 2026-07-27 audit).

`n_done` is incremented on both the success and failure paths:

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: failure advances done counter
    continue
n_done += 1
```

Both terminal conditions (`nxt.value is None` and `--max-tracks` hit) return 0
unconditionally — no call to `exit_status()` from `loop_hardening`. A full-
failure run (all tracks quarantined) logs "done (processed N, quarantined N)"
and returns 0. CI/monitoring cannot distinguish this from genuine success.

`mac_analyze_loop.py` already implements the correct pattern via
`exit_status(done, failed, persist_failed)`.

**Fix:** Separate `n_done` (successes) from `n_failed` (failures); call
`exit_status()` at both return sites.

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` `sha256_file` call lacks `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–462  
**Class:** B (missing integrity-check guard).  
**Status:** Confirmed present (unchanged).

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

`sha256_file` opens the file with `open(path, "rb")` — it raises `OSError` if
the file is missing or unreadable. An unhandled `OSError` here propagates out of
the main loop body uncaught (no outer `OSError` handler), killing the analysis
thread for that track without calling `persist_failed_inc()`. The analogous call
in the (now-deleted) `set_mert_backfill_loop.py` had an `OSError` guard. One-
liner fix: wrap in `try/except OSError`.

### 3.3 LOW (carried) · C3 — `mac_analyze_loop.py` `_persist_in_bg` exception scope too narrow

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424  
**Class:** C3 (honest counting).  
**Status:** Confirmed present.

```python
try:
    rsync_stems_out(stem_local, tid)
    push_track_rows(tid)
    counts.done_inc()
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
```

An `OSError` (stem directory missing on write) or `sqlite3.OperationalError`
(scratch DB lock timeout) from `push_track_rows` or `rsync_stems_out` propagates
uncaught out of the background thread. `persist_failed_inc()` is never called,
leaving `Counts` under-reporting persist failures. Thread exits silently without
the main loop being notified.

### 3.4 MEDIUM (new) · B/C — `rescue_common.py::phase2_replace()` drops retiring sha256 from `content_history`

**File:** `scripts/rescue_common.py` · Lines ~87–110  
**Class:** B + C hybrid — missing integrity ledger write before destructive DELETE.  
**Status:** Confirmed present (new this audit).

`replace_track_audio.py`'s `_delete_old_row_if_exists()` atomically records the
retiring row's sha256 in `content_history` (same transaction as the DELETE) per
spec P9/B2 "never-drop-hash":

```python
if row["sha256"]:
    append_generation_on(conn, Generation(..., content_sha256=row["sha256"], ...))
conn.execute("DELETE FROM track_audio WHERE track_audio_id = ?", ...)
conn.commit()
```

`rescue_common.py::phase2_replace()` (used by `redownload_via_ytmusic` and
`redownload_via_spotdl`) does a bare DELETE with no such recording:

```python
with connect(db_path) as conn:
    conn.execute("DELETE FROM track_audio WHERE track_audio_id = ?", (old_taid,))
    conn.commit()
```

Any GT clip content-bound to the retiring row's bytes loses its evidence when
either rescue script runs Phase 2. The `redownload_via_ytmusic` Phase 2 path can
process tens of rows per run. The reconcile_orphans sweep cannot reconstruct a
sha256 after the row is gone.

**Fix:** Read the retiring row's sha256 + recording_id + stem + variant before
the DELETE, then call `append_generation_on()` in the same transaction, matching
the `_delete_old_row_if_exists` contract.
