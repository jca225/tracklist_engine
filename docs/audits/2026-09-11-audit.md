## 3. Open findings

### 3.1 HIGH · C (carried) — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines 359–372

**Severity upgrade from MEDIUM → HIGH** — this is the sole GPU-batch entry
point and runs on rented hardware with a cost target; silent all-fail with
exit 0 wastes the entire budget with no signal.

`n_done += 1` fires on both the success path (line 369) and the failure
`continue` path (line 364). Both `return 0` exits (lines 337 and 372) are
unconditional. Consequences:

1. A GPU run where every track fails logs "done (processed N, quarantined 0)"
   and exits 0 — CI/scheduler treats it as success.
2. `--max-tracks N` is driven by `n_done`; ten consecutive failures exhaust the
   limit with zero analysis records written, exit 0.
3. `_load_audio_asset` failures at lines 353–357 add to `failed_tids` but are
   not counted anywhere — they vanish from the final drain log entirely.

Compare `mac_analyze_loop.py` which calls `exit_status(done, failed, pf)` and
escalates to ERROR + nonzero when `n_done == 0` or failure ratio is high.

**Fix:** increment a separate `n_failed` counter on the failure path; call
`loop_hardening.exit_status(n_done, n_failed)` at both return sites; tally
`_load_audio_asset` misses separately so the drain log is honest.

### 3.2 MEDIUM · C (carried, upgraded) — `mac_analyze_loop.py _persist_in_bg` catches only `CalledProcessError`

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

`subprocess.TimeoutExpired` is a sibling of `CalledProcessError` (both inherit
`SubprocessError`), not a subclass. If `rsync_stems_out` or `push_track_rows`
times out, the exception escapes the handler, `persist_failed_inc()` is never
called, and the background thread terminates silently. The main loop's
`bg.join()` returns normally; `exit_status()` then sees an understated
`n_persist_failed` and may return 0 for a run where results were never written
to the canonical DB.

Previously graded LOW as "exception scope too narrow"; upgrading to MEDIUM
because `TimeoutExpired` is a realistic event on a flaky Tailscale connection
and the consequence (silent persist failure counts as success) is the same
class-C pattern as finding 3.1.

**Fix:** widen to `except subprocess.SubprocessError` or add a separate
`except subprocess.TimeoutExpired` arm calling `persist_failed_inc()`.

### 3.3 LOW (carried) — `mac_analyze_loop.py` sha256 `OSError` guard missing

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError

```

An `OSError` (file truncated, NFS stale handle) propagates uncaught, killing
the analysis thread for that track and leaving `persist_failed_inc()` uncalled.
`loop_prefetch.py` guards the equivalent call; `mac_analyze_loop.py` does not.

### 3.4 LOW (new) · B — `mac_analyze_loop.py` rsync calls missing SSH keepalive opts

**File:** `scripts/mac_analyze_loop.py` · Lines ~178, ~199 (`rsync_in`,
`rsync_stems_out`)

Both rsync calls do not pass `-e "ssh <SSH_OPTS>"`. `SSH_OPTS` in
`loop_hardening.py` includes `ServerAliveInterval=15 ServerAliveCountMax=3`,
which kills a dead Tailscale pipe in ~45 s. Without it, rsync's internal SSH
session has no keepalive and can hang indefinitely on a dead link — the
wall-clock subprocess `timeout=RSYNC_TIMEOUT` (600 s) is the only backstop.

Impact: bounded by the 600 s timeout, so this is latent, not a blocker. But the
gap means a Tailscale reconnect (common in mobile home office setups) silently
blocks for up to 10 min per rsync instead of recovering in 45 s.

### 3.5 LOW (new) · A — `replace_track_audio.py` `text=True` without `encoding=`

**File:** `scripts/replace_track_audio.py` · Line 650

```python
out = subprocess.run(
    [..., "ffprobe", ...],
    capture_output=True,
    text=True,         # ← no encoding=
    timeout=10,
)
```

ffprobe output is ASCII numerics in practice; this is latent/hardening. Fix:
add `encoding="utf-8"` to match `loop_hardening.TEXT_KW`.

### 3.6 LOW (new) · A — `analysis/persistence.py` `.decode()` without explicit encoding

**File:** `analysis/persistence.py` · Line 83

```python
subprocess.check_output(["git", "rev-parse", ...], stderr=subprocess.DEVNULL)
.decode()
```

Git short SHA is always hex ASCII so Latin-1 vs UTF-8 is moot in practice;
marked latent/hardening. Fix: add `encoding="utf-8"` or use
`text=True, encoding="utf-8"`.
