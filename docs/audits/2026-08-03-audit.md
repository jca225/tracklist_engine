## 3. Open findings

### 3.1 MEDIUM · C1+C3 — `gpu_worker.py`: `n_done` incremented on failure, always returns 0 (carried since 2026-07-27)

**File:** `analysis/gpu_worker.py` · Lines ~356–372

Not fixed. `n_done` is incremented on both success and failure paths (lines 364
and 369); both exit points return `0` without calling `exit_status()`.

- A GPU box run where every track fails exits 0 — CI/cron treats it as success.
- `--max-tracks N` is driven by `n_done`, so N consecutive failures exhaust the
  limit without successfully analyzing any track; caller receives exit 0.

**Fix:** Increment `n_failed` (not `n_done`) on failure; call
`exit_status(n_done, n_failed)` at both return sites, matching
`mac_analyze_loop.py`'s established pattern.

### 3.2 MEDIUM (upgraded from LOW) · C3 — `mac_analyze_loop.py _persist_in_bg`: `subprocess.TimeoutExpired` escapes except clause

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424

The background persist thread `_persist_in_bg` only catches
`subprocess.CalledProcessError`:

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

`subprocess.TimeoutExpired` is **not** a subclass of `CalledProcessError` — it
is a sibling class under `subprocess.SubprocessError`. Both `rsync_stems_out`
and `push_track_rows` call `subprocess.check_call` / `subprocess.run` with
explicit timeouts (`RSYNC_TIMEOUT=600`, `SSH_PUSH_TIMEOUT=300`); when either
fires, `TimeoutExpired` is raised and escapes this clause.

Consequence: the background thread terminates without calling
`persist_failed_inc()`, violating the C3 honest-count guarantee established in
`loop_hardening.py`. `exit_status()` receives `n_persist_failed=0` when it
should be nonzero, potentially reporting a clean exit on a run with stuck
rsync/ssh transfers.

The prior audit (2026-07-27, finding 3.4) described this gap in terms of
`OSError` / `sqlite3.OperationalError`. Those exceptions can also escape, but
`TimeoutExpired` is the more likely production trigger and is confirmed present.

**Fix:** Widen the except clause to `except (subprocess.CalledProcessError,
subprocess.TimeoutExpired) as e:` (or the broader `except Exception` with
`log.exception` to also cover the `OSError` / `sqlite3` cases from 3.4).

### 3.3 LOW (carried) · B — `mac_analyze_loop.py`: `sha256_file` without `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

`set_mert_backfill_loop.py` (now deleted) had the guard;
`mac_analyze_loop.py` does not. An `OSError` here would propagate into the
main try/except, hit the `CalledProcessError` clause (which won't match), and
terminate the loop for that track without proper accounting.

**Fix:** Wrap in `try/except OSError`.
