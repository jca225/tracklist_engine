### [HIGH / LATENT] C2 — `analysis/vast_worker.py --loop` no poison-pill quarantine

**File:** `analysis/vast_worker.py`, lines 247–279
**Class:** C2 — poison-pill retry (failed track re-queued indefinitely)

`_next_unanalyzed` selects `WHERE track_analysis IS NULL`. When `_process_one`
fails (e.g. corrupt audio, bad ffprobe output), `n_done` is incremented and the
loop `continue`s — but the `track_audio_id` is **never added to a skip set**.
On the next iteration the same predicate picks the same corrupt track again.
With `--max-tracks None` (the default), this spins forever on a single bad file.

This is exactly the bug class fixed in `vast_loop.py` after the track-149
incident (496 consecutive failures before the `failed_tids` quarantine landed).
`vast_worker.py --loop` is the superseded code path but remains invocable; a
user who rents a Vast box and runs the old worker directly would hit this.

**Risk:** indefinite spin on a corrupt track, GPU-hours wasted, no forward
progress.
**Mitigation:** `vast_loop.py` is the production path. `vast_worker.py` is
not documented in the README as the entry point, but it is not removed either.

**Recommended fix:** either delete `--loop` mode from `vast_worker.py` or add a
`failed_tids` set matching the `vast_loop.py` pattern.

### [MEDIUM / CONFIRMED] B-DB — `scripts/mac_analyze_loop.py` missing `PRAGMA busy_timeout`

**File:** `scripts/mac_analyze_loop.py`, `push_track_rows()`, line ~287
**Class:** B — missing integrity guard (concurrent DB lock not handled)

`push_track_rows()` opens the canonical DB transaction with:

```python
sql_lines = [".bail on", "BEGIN;", ...]
```

`scripts/vast_loop.py` (reference) uses:

```python
sql_lines = [".bail on", "PRAGMA busy_timeout=120000;", "BEGIN IMMEDIATE;", ...]
```

Without `PRAGMA busy_timeout`, SQLite returns `SQLITE_BUSY (5)` immediately
when a pi-storage writer holds the lock. Without `BEGIN IMMEDIATE`, a deferred
transaction can deadlock against a concurrent writer mid-transaction.

`subprocess.CalledProcessError` from sqlite3 exit-nonzero is caught at the
loop level and adds the `track_audio_id` to `failed_tids` — so a transient DB
lock permanently quarantines the track for this process run, wasting ~200–250 s
of Mac MPS analysis work per incident.

**Recommended fix:** prepend `"PRAGMA busy_timeout=120000;"` and change `"BEGIN;"` to
`"BEGIN IMMEDIATE;"` in `push_track_rows()`, matching `vast_loop.py`.

### [LOW / LATENT] B1 — `scripts/ingest_stem_url.py` main SSH call has no timeout

**File:** `scripts/ingest_stem_url.py`, line ~604
**Class:** B1 — missing subprocess timeout

```python
r = subprocess.run(
    ssh_cmd, capture_output=True, text=True, encoding="utf-8", errors="replace"
)
```

No `timeout=`, no `SSH_OPTS` (ConnectTimeout / ServerAliveInterval). If
yt-dlp on pi-storage hangs (bot detection, broken connection), the Mac process
hangs indefinitely with no output (all output buffered until completion due to
`capture_output=True`).

Severity is Low because this is an interactive one-shot tool (the user can
Ctrl+C) rather than an unattended loop. However the hang is invisible — the
terminal shows no progress for an arbitrary duration.

**Recommended fix:** add `timeout=SSH_PUSH_TIMEOUT` and splice `SSH_OPTS` into
`ssh_cmd`, matching the pattern in `loop_hardening.py`.
