## 3. Open findings

### 3.1 MEDIUM (carried ~2.5 months) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~364, 369, 307, 337, 372

First reported: 2026-07-27 audit §3.1. Still present, unmodified.

`n_done` advances on both the success and failure paths. Every return site is
`return 0` — no call to `loop_hardening.exit_status`:

```python
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← failure counted as done (C3)
    continue
_log.info("OK [%d] ...", n_done + 1, ...)
n_done += 1
...
return 0                 # ← always success (C1)
```

Consequence: a GPU box run where every track fails exits 0. CI/monitoring treats
it as success. `--max-tracks N` exhausts on consecutive failures, returns 0,
writes nothing.

**Fix:** rename the failure-path increment to `n_failed += 1`; call
`loop_hardening.exit_status(n_done, n_failed)` at all three return sites.

### 3.2 MEDIUM (new) · C — `mac_analyze_loop.py` main loop misses `TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Line ~517

The main per-track try/except catches only `subprocess.CalledProcessError`.
`subprocess.TimeoutExpired` is NOT a subclass of `CalledProcessError` — both
are siblings under `SubprocessError`. `rsync_in`, `ssh_pi` (called by
`fetch_asset` and `next_task`), and `push_track_rows` all have
subprocess-timeout guards (`RSYNC_TIMEOUT=600s`, `SSH_QUERY_TIMEOUT=120s`)
that raise `TimeoutExpired` on expiry.

When `TimeoutExpired` fires:
1. The `finally` block runs (local file cleanup — correct).
2. The exception propagates out of the `while True` loop.
3. `main()` terminates with an unhandled exception — the entire analysis
   session is gone.

In practice, SSH keepalives (`ServerAliveInterval=15`, `CountMax=3`) detect
dead connections in ~45s → `CalledProcessError`, and rsync `--timeout=300`
aborts I/O stalls → `CalledProcessError`. The subprocess timeout (600s / 120s)
is only reached for a transfer that is alive but producing no I/O, which is
rare. When it does happen, one bad pull kills the whole loop rather than being
retried (C2 goal: bounded retry) or quarantined.

The comment on that except clause says "timeout, broken pipe" — the intent is
clear; the code missed `TimeoutExpired`.

**Fix:**
```python
except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:
    # ...existing register_transient logic...
```

### 3.3 LOW (carried) · C3 — `mac_analyze_loop._persist_in_bg` catches only `CalledProcessError`

**File:** `scripts/mac_analyze_loop.py` · Lines ~419–424

Background thread `_persist_in_bg` catches only `subprocess.CalledProcessError`.
`TimeoutExpired` (from `rsync_stems_out` or `push_track_rows`), `OSError`
(scratch DB path missing), or `sqlite3.OperationalError` (lock collision beyond
`busy_timeout`) would silently terminate the thread without calling
`counts.persist_failed_inc()`. The loop continues, but honest tally (C3) is
broken: `exit_status` sees fewer persist failures than actually occurred.

**Fix:** widen to
`except (subprocess.SubprocessError, OSError, sqlite3.OperationalError) as e:`.

### 3.4 LOW (carried) · B — `mac_analyze_loop.py` sha256_file missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Line ~455

`sha256_file(local_audio)` can raise `OSError` if the rsync appears to succeed
but the file lands at an unexpected path (or is unlinked between the rsync
return and the open). `OSError` escapes the `except CalledProcessError` handler
and crashes `main()`. Covered by the fix for finding 3.2 (widening the except
clause catches `OSError` too).
