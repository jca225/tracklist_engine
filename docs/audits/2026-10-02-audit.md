## 3. Findings

### 3.1 MEDIUM (carry + upgrade) · C3 — `mac_analyze_loop._persist_in_bg` uncaught `subprocess.TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Lines ~419–424

Prior audit (2026-07-27 §3.4) graded this LOW, citing `OSError` and
`sqlite3.OperationalError` as the uncaught exception classes. This pass
confirms the specific — and most likely real-world — path is
`subprocess.TimeoutExpired`, upgrading to MEDIUM.

`_persist_in_bg` catches only `subprocess.CalledProcessError`:

```python
try:
    rsync_stems_out(stem_local, tid)   # check_call(..., timeout=RSYNC_TIMEOUT=600)
    push_track_rows(tid)               # run(..., timeout=SSH_PUSH_TIMEOUT=300)
    counts.done_inc()
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error(...)
```

Both `rsync_stems_out` and `push_track_rows` use subprocess calls with explicit
timeouts (`RSYNC_TIMEOUT=600s`, `SSH_QUERY_TIMEOUT=120s`, `SSH_PUSH_TIMEOUT=300s`).
When a timeout fires, `subprocess.TimeoutExpired` is raised — a sibling of
`CalledProcessError` in `subprocess.SubprocessError`, NOT a subclass of it.
Python's default `threading.excepthook` prints the traceback and lets the thread
terminate silently. Consequences:

1. `counts.persist_failed_inc()` is NOT called — honest-count (C3) fails.
2. `exit_status()` sees fewer `persist_failed` than actual, potentially
   returning exit 0 + INFO "queue drained" when some pushes timed out.
3. Stems and DB rows for the affected track are dropped without retry; the
   track has no `track_analysis` row so it will be re-selected and re-analyzed
   from scratch next session.

**Status:** confirmed present.

**Fix:** widen the except clause:
```python
except (subprocess.CalledProcessError, subprocess.TimeoutExpired, OSError) as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed (%s): %s", tid, type(e).__name__, e)
```

### 3.2 MEDIUM (carry) · C1+C3 — `gpu_worker.py` loop mode always exits 0

**File:** `analysis/gpu_worker.py` · Lines ~324–372

Unchanged from 2026-07-27 finding 3.1. `n_done` is incremented on both success
and failure paths; both exit conditions (`return 0` at line ~337 and ~371)
return unconditionally. A session where all tracks fail exits 0 + INFO "no
unanalyzed tracks remain" — CI/cron treats as success.

`mac_analyze_loop.py` uses `exit_status()` from `loop_hardening.py` which
escalates to nonzero+ERROR when `n_done == 0` or failure ratio is high.
`gpu_worker.py` (the renamed `vast_worker`) does not import or call it.

**Fix:** separate `n_failed` from `n_done`; call `exit_status(n_done, n_failed)`
at both return sites.

### 3.3 LOW (carry) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

Unchanged from 2026-07-27 finding 3.2. `sha256_file(local_audio)` can raise
`OSError` if the rsync wrote a partial file and it vanished before the sha check
runs. The outer `except subprocess.CalledProcessError` does not catch `OSError`,
so this would crash the loop process rather than quarantining the track.
Latent — requires a partial rsync + immediate file deletion race.
