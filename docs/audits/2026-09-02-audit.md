## 3. New findings

### 3.1 HIGH · A2+B1 — `core/ssh_sqlite.py` missing timeout and encoding (confirmed present)

**File:** `core/ssh_sqlite.py` · Lines 28–34

**Class:** A (encoding/mojibake) + B (missing timeout)

`ssh_sqlite` is the canonical primitive for SSH+sqlite queries to pi-storage,
used by all labeling scripts (`pull_set_for_alignment.py`, `tag_aligning_folder.py`,
`reconcile_aligning_manifest.py`, `inventory_check.py`, `remap_gt_slot_labels.py`,
`enrich_gt_track_ids.py`). It has two gaps not present in the hardened loop scripts:

**B1 — no subprocess timeout:**
```python
cmd = ["ssh", "-o", "ConnectTimeout=15", host, f"sqlite3 {db}"]
out = subprocess.run(
    cmd,
    input=script,
    capture_output=True,
    text=True,
    check=True,
    # ← no timeout=
)
```
`ConnectTimeout=15` bounds the TCP handshake but not query execution. If sqlite3
stalls (e.g. DB write-locked under a long bulk push from `mac_analyze_loop`), the
subprocess hangs indefinitely, blocking whatever labeling script called it.
`loop_hardening.SSH_QUERY_TIMEOUT = 120` and `SSH_OPTS` (ServerAliveInterval/CountMax)
exist precisely for this — `ssh_sqlite` does not use them.

**A2 — no explicit encoding:**
```python
text=True,
# ← no encoding="utf-8", errors="surrogateescape"
```
Python falls back to the system locale. On pi-storage (Linux aarch64), if
`LANG` is not UTF-8 (common in headless/daemon contexts), a non-ASCII byte in
a track path or title (e.g. "… (Official Karaoke) ｜ SongJam.wav", a real
failure class noted in `mac_analyze_loop.py`) raises `UnicodeDecodeError` and
kills the caller. Even with UTF-8 locale, a genuinely Latin-1-encoded byte
(legacy DB row) causes silent mojibake in the returned JSON rows.
`loop_hardening.TEXT_KW` defines the correct triple; `ssh_sqlite` predates it.

**Fix:** add `timeout=120, encoding="utf-8", errors="surrogateescape"` and
include `SSH_OPTS` (ServerAliveInterval/CountMax) in the ssh command. See
`mac_analyze_loop.ssh_pi` for the hardened template.

**Failure scenario:** a labeling session runs `pull_set_for_alignment.py` while
`mac_analyze_loop` is mid-push; the sqlite3 write lock holds for >120s; the
ssh process hangs; the labeling script blocks forever with no timeout log.
Alternatively: a track with a non-UTF-8 filename in `track_audio.path` causes
`UnicodeDecodeError` and kills the caller mid-inventory-check.

### 3.2 MEDIUM · C1 — `ingest/main_retry.py` always returns 0 (latent)

**File:** `ingest/main_retry.py` · Line 417

**Class:** C (dishonest exit code)

`_run` unconditionally returns `0`, even when every candidate timed out:

```python
    elapsed = time.monotonic() - t0
    _log.info("DONE | candidates=%d downloaded=%d timeout=%d gone=%d ...", ...)
    return 0   # ← always, regardless of downloaded vs failed ratio
```

If spotdl hits its Spotify rate-limit wall (24h backoff after threshold — a risk
the script's own docstring calls out), 100% of attempts will timeout and the
script still exits 0. A cron or CI caller reads this as success. Compare: the
`loop_hardening.exit_status` contract (used by `mac_analyze_loop.py`) escalates
to nonzero+ERROR when `n_done == 0` or failure ratio exceeds 50%.

The `all-unavailable` case (every track is genuinely gone from Spotify) is a
legitimate 0-downloads-but-success situation, so a blanket "zero downloads = 1"
is wrong. The distinction that matters is **timeout** vs **unavailable**:
100% timeout is a network/rate-limit failure; 100% unavailable is an expected
data-quality outcome. The fix would return nonzero only when
`failed_timeout / candidates > 0.5` (or any value of `db_failed > 0`).

**Failure scenario:** spotdl hits rate-limit backoff; a cron job fires
`ingest/main_retry.py` overnight across 300 candidates; all 300 timeout; script
exits 0; monitoring treats the run as a no-op success; the re-download gap
accumulates silently.

Graded latent: the script is a manual targeted-retry tool, not a daily cron
job, so the failure surface is lower than in `gpu_worker`. But it fits the same
pattern as the prior `gpu_worker.py` C1 finding.
