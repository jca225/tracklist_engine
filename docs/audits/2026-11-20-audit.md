## 3. Open findings

### 3.1 MEDIUM (pre-existing) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~324–372

Unchanged since 2026-07-27. `n_done` is incremented on both the failure path
(`if not r.is_ok(): n_done += 1`) and the success path. Both terminal conditions
(`queue drained`, `--max-tracks` hit) `return 0` without calling
`loop_hardening.exit_status()`. A session where every track fails logs at WARNING
but exits 0; CI/cron treats it as success. `--max-tracks` quota exhausts on
failures with no records written.

**Fix:** increment `n_failed` (not `n_done`) on the failure path; call
`exit_status(n_done, n_failed)` at both return sites, mirroring
`mac_analyze_loop.py`.

### 3.2 LOW (pre-existing) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Line 455

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
```

An `OSError` here (rsync exit-0 but file unreadable, e.g. race with cleanup)
propagates uncaught through the outer `try/except CalledProcessError` block,
killing the main loop iteration without calling any `failed_inc()`. The same
pattern in `mert_backfill_loop.py` had an OSError guard — that file is now
deleted, leaving this instance unpatched.

**Fix:** wrap in `try/except OSError as exc: local_sha = f"<unreadable: {exc}>"`.

### 3.3 MEDIUM (new) · C1 — `ingest/main_retry.py` always returns exit code 0

**File:** `ingest/main_retry.py` · Line 416

`_run()` unconditionally `return 0` after the main loop regardless of outcome.
If all Spotify retry candidates time out or fail (a real scenario when bundled
spotdl creds are rate-limited), the final log line reads:

```
INFO … DONE | candidates=500 downloaded=0 timeout=500 gone=0 other=0 db=0 in 30000s
```

but the process exits 0. Any downstream CI step, cron alerting, or orchestration
that checks the exit code treats the run as success.

`mac_analyze_loop.py` already imports `loop_hardening.exit_status` for this
exact purpose. This file predates that import and was never updated.

**Fix:** replace the terminal `return 0` with:
```python
total = stats.downloaded + stats.failed_timeout + stats.failed_other + stats.db_failed
n_failed = stats.failed_timeout + stats.failed_other + stats.db_failed
code, _, msg = exit_status(stats.downloaded, n_failed)
_log.log(logging.ERROR if code else logging.INFO, "%s", msg)
return code
```

### 3.4 LOW (pre-existing, scope expanded) · C3 — `_persist_in_bg` catches only `CalledProcessError`, not `TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424

The `except subprocess.CalledProcessError` block does not catch
`subprocess.TimeoutExpired`. Both `rsync_stems_out()` and `push_track_rows()`
call `subprocess.check_call` / `subprocess.run` with explicit timeouts
(`RSYNC_TIMEOUT=600s`, `SSH_PUSH_TIMEOUT=300s`). When a timeout fires:

- `subprocess.TimeoutExpired` escapes the `except` clause
- The background thread terminates silently (Python does not propagate thread
  exceptions to the parent)
- Neither `counts.done_inc()` nor `counts.persist_failed_inc()` is called
- The track is permanently orphaned from accounting: counted in `n_seen` but
  absent from both done and failed totals
- `exit_status()` sees an artificially low denominator, may not escalate

An rsync stall of >600s is a realistic failure mode on a flaky Tailscale leg.

**Fix:** broaden the except clause:
```python
except (subprocess.CalledProcessError, subprocess.TimeoutExpired, OSError, Exception) as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```
(Or at minimum `subprocess.SubprocessError`, which covers both
`CalledProcessError` and `TimeoutExpired`.)
