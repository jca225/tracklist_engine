### Class A — Encoding / Mojibake

#### A1 · **HIGH · confirmed** — `mac_analyze_sets.py:ssh_pi()` and `push_set_rows()` use `text=True` without UTF-8 encoding

**File:** `scripts/mac_analyze_sets.py:50-52, 148-149`

```python
# ssh_pi (line 50-52)
r = subprocess.run(["ssh", PI_HOST, full],
                   capture_output=True, text=True, check=True)
#                                    ^^^^^^^^^ no encoding/errors= kwargs

# push_set_rows (line 148-149)
subprocess.run(["ssh", PI_HOST, f"sqlite3 {CANONICAL_DB}"],
               input=full, text=True, check=True)
#                           ^^^^^^^^^ no encoding/errors= kwargs
```

`text=True` without `encoding='utf-8', errors='surrogateescape'` uses the process
locale (often Latin-1 on pi-storage) to decode stdout. A track title containing a
non-ASCII byte (e.g. an em-dash, accented character) in a path or set_id output can
corrupt silently. `mac_analyze_loop.py` — the sibling script — explicitly pins UTF-8
everywhere via `loop_hardening.TEXT_KW`. `mac_analyze_sets.py` never imported
`loop_hardening` and missed this fix.

**Failure scenario:** ssh_pi() returns a path containing a non-ASCII character;
Python decodes it with the locale codec (Latin-1 on pi-storage → mismatched bytes);
the resulting garbage path is passed to rsync_in(), which tries to open a nonexistent
file, failing with exit code 23. The set is skipped without any quarantine or retry.

### Class B — Missing Subprocess / rsync Timeouts

#### B1 · **HIGH · confirmed** — `mac_analyze_sets.py` has no SSH_OPTS, no subprocess timeouts, no rsync I/O timeout on any of its four subprocess calls

**File:** `scripts/mac_analyze_sets.py:50, 93, 99-102, 148`

```python
# ssh_pi — no SSH_OPTS, no timeout=
subprocess.run(["ssh", PI_HOST, full], capture_output=True, text=True, check=True)

# rsync_in — no --timeout, no subprocess timeout=, no shlex.quote on remote path
subprocess.check_call(["rsync", "-q", f"{PI_HOST}:{remote_path}", str(local)])

# rsync_stems_out — no SSH_OPTS on mkdir, no timeout= on either call
subprocess.check_call(["ssh", PI_HOST, f"mkdir -p ..."])
subprocess.check_call(["rsync", "-aq", src, dst])

# push_set_rows — no SSH_OPTS, no timeout=
subprocess.run(["ssh", PI_HOST, f"sqlite3 {CANONICAL_DB}"], ...)
```

`mac_analyze_loop.py` (the per-track sibling) imports `SSH_OPTS`, `SSH_QUERY_TIMEOUT`,
`SSH_PUSH_TIMEOUT`, `RSYNC_TIMEOUT`, and `RSYNC_IO_TIMEOUT` from `loop_hardening.py`
and passes them to every subprocess call. `mac_analyze_sets.py` never had this treatment.

`rsync_in()` also lacks `shlex.quote()` on the remote path — a regression relative to
`mac_analyze_loop.py`'s explicit fix (see comment in that file dated 2026-07-10
referencing `"… (Official Karaoke Instrumental) ｜ SongJam.wav"`). A set audio file
with parentheses or pipes in its name would cause rsync to abort with exit 2.

**Failure scenario (hang):** The Tailscale SOCKS tunnel between Mac and pi-storage
drops mid-transfer. `ssh_pi()` hangs indefinitely (no `ServerAliveInterval`); the Mac
analysis loop stalls for hours until the operator kills it.

**Failure scenario (data loss):** A set audio filename contains a space or parenthesis;
`rsync_in()` emits `rsync: [receiver] failed to connect to pi-storage (exit 2)` and
the set is silently dropped (the `CalledProcessError` unwinds without quarantine).

### Class C — Silent Failure Loops

#### C1 · **HIGH · confirmed** — `mac_analyze_sets.py` main loop: unhandled `CalledProcessError` from `rsync_stems_out` or `push_set_rows` aborts the entire batch

**File:** `scripts/mac_analyze_sets.py:188-234`

```python
for asset in pending:
    ...
    rsync_in(asset.path, local_audio)    # CalledProcessError → unhandled, exits
    ...
    match result:
        case Ok(r): ...
        case Err(e): ...continue
    rsync_stems_out(local_set_dir, sid)  # CalledProcessError → unhandled, exits
    push_set_rows(r, local_audio)        # CalledProcessError → unhandled, exits
```

Any subprocess failure in the fetch or push path raises `CalledProcessError` which
propagates to the caller and terminates the script entirely. All remaining sets in
`pending` are abandoned. No partial-failure counter, no quarantine, no `exit_status()`
call, no nonzero return code.

Compare with `mac_analyze_loop.py`: the push is wrapped in a background thread that
catches `subprocess.CalledProcessError` and increments `counts.persist_failed`, and
the main loop has its own `except subprocess.CalledProcessError` for the fetch path.

**Failure scenario:** First set in the batch has an audio file on a path that rsync
temporarily can't reach (pi-storage rebooting). `rsync_in` raises `CalledProcessError`.
Script exits with traceback, status 1. Remaining N-1 sets wait forever. Operator sees
a truncated log and must manually restart.

#### C2 · **MEDIUM · confirmed** — `analysis/gpu_worker.py` loop mode: failures increment `n_done`, so `--max-tracks` budget is consumed by poison files and exits 0 ("success")

**File:** `analysis/gpu_worker.py:359-364`

```python
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1   # ← same counter as successes
    continue
...
# at the end of the while loop, when max_tracks is hit:
_log.info("hit --max-tracks=%d, stopping", args.max_tracks)
return 0           # ← always 0, even if every track failed
```

`n_done` counts both successes and quarantined failures. With `--max-tracks=5`, if
every track fails, `n_done` reaches 5, the loop exits with `return 0`, and the caller
sees "hit --max-tracks=5, stopping" at INFO level — indistinguishable from a healthy
smoke run.

This is a C3/C1 cross-cut: the counting is dishonest AND the exit code doesn't
distinguish all-fail from all-ok in bounded mode. Smoke tests that use `--max-tracks`
to gate deploys can silently pass when every analysis step errored.

**Failure scenario:** Deploy gating smoke test runs `gpu_worker --loop --max-tracks 3`.
A mis-configured model path causes `analyze_track` to fail on all 3 tracks. Worker
exits 0 with "hit --max-tracks=3". CI passes. Broken config ships to the full corpus
run.

#### C3 · **MEDIUM · latent** — `ingest/main_retry.py` always exits 0, even when all downloads fail or DB writes fail

**File:** `ingest/main_retry.py:417`

```python
# _run() ends:
_log.info("DONE | candidates=%d downloaded=%d timeout=%d gone=%d other=%d db=%d in %.0fs",
          stats.candidates, ...)
return 0   # ← unconditional; db_failed and failed_other not interrogated
```

If the whole Spotify retry batch times out, or DB inserts fail for every candidate, the
script still returns 0. A cron or pipeline step that calls `main_retry` and checks the
return code for "did anything go wrong?" gets a false green. Grade latent because
`main_retry` is typically run manually / observed via logs, not gated by CI.
