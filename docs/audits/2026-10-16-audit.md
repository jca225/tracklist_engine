## 3. Open findings

### 3.1 MEDIUM · C1+C3 — `gpu_worker.py` `n_done` / `return 0` (carried)

**File:** `analysis/gpu_worker.py` · Lines 364, 337, 372

**Class:** C (silent-failure loop) — C3 honest-counting + C1 honest exit code.

`n_done` is incremented on the failure path (line 364) as well as the success
path (line 369). Both terminal exits (`return 0` at line 337 on drain, `return 0`
at line 372 on `--max-tracks`) fire without calling `exit_status()`:

```python
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: done counter advanced on failure too
    continue
...
n_done += 1              # success path

if nxt.value is None:
    _log.info("no unanalyzed tracks remain — done ...")
    return 0             # ← C1: no exit_status() call; always 0
...
return 0                 # ← C1: same on --max-tracks
```

A GPU box run where every track is a poison pill exits with code 0 and a
cheerful "no unanalyzed tracks remain" INFO log. Compare: `mac_analyze_loop.py`
calls `exit_status(done, failed, pf)` which escalates to nonzero+ERROR when
`done == 0` or failure ratio is high.

**Fix:** separate `n_done` (successes) from `n_failed` (failures); call
`exit_status(n_done, n_failed)` at both return sites.

### 3.2 LOW · B — `mac_analyze_loop.py` sha256_file missing `OSError` guard (carried)

**File:** `scripts/mac_analyze_loop.py` · Lines 454–463

`sha256_file(local_audio)` is called without a `try/except OSError`:

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no OSError guard
    if local_sha != asset.sha256:
```

An `OSError` (disk read error in the window between rsync exit and sha256 check)
propagates to the outer `except subprocess.CalledProcessError`, which does NOT
catch `OSError`, so the exception escalates further and kills the main-thread
iteration uncleanly. The track is neither counted as done nor as failed — the
loop state is inconsistent.

`set_mert_backfill_loop.py` (now retired) had the same pattern with the guard:
```python
try:
    local_sha = sha256_file(local_audio)
except OSError as exc:
    local_sha = f"<unreadable: {exc}>"
```

**Fix:** wrap `sha256_file` call in `try/except OSError` and treat it like a
sha-mismatch (transient failure path).

### 3.3 LOW · C3 — `_persist_in_bg` exception scope too narrow (carried)

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424

`_persist_in_bg` catches only `subprocess.CalledProcessError`. Three other
exception classes terminate the bg thread silently without calling
`persist_failed_inc()`:

- `subprocess.TimeoutExpired` — raised when `rsync_stems_out` or `push_track_rows`
  hits a subprocess wall-clock limit. Most likely failure mode on a 36-hour
  weekend run if Tailscale drops.
- `OSError` — if the scratch DB path disappears mid-run.
- `sqlite3.OperationalError` — lock timeout on scratch-DB write.

When the thread dies, `counts.done_inc()` is not called and neither is
`persist_failed_inc()`. The track disappears from all counters. When the queue
drains, `exit_status(0, 0, 0)` returns code 0 — a run where all bg pushes timed
out reads as "analyzed 0, failed 0 — success".

**Fix:** widen the except clause to `except Exception`, or enumerate the
additional types. `persist_failed_inc()` must be called for any unhandled
exception.

### 3.4 NEW · LOW · B — rsync_in / rsync_stems_out missing SSH_OPTS in rsync transport

**File:** `scripts/mac_analyze_loop.py` · Lines 178–188, 195–203

Both rsync calls omit `-e "ssh <SSH_OPTS>"`:

```python
# rsync_in
subprocess.check_call(
    ["rsync", "-q", "--timeout", str(RSYNC_IO_TIMEOUT),
     f"{PI_HOST}:{shlex.quote(remote)}", str(local)],
    timeout=RSYNC_TIMEOUT,
)

# rsync_stems_out
subprocess.check_call(
    ["rsync", "-aq", "--timeout", str(RSYNC_IO_TIMEOUT), src, dst],
    timeout=RSYNC_TIMEOUT,
)
```

rsync uses `ssh` as its transport when the destination is `host:path`. Without
`-e "ssh -o BatchMode=yes -o ConnectTimeout=15 -o ServerAliveInterval=15
-o ServerAliveCountMax=3"`, the SSH layer backing rsync:

1. Lacks `BatchMode=yes` — a stale SSH key prompts for a password and blocks
   up to `RSYNC_TIMEOUT = 600s` instead of fast-failing.
2. Lacks `ServerAliveInterval` — a dead Tailscale relay takes the full
   socket-stall period to detect instead of ~45s.

The subprocess `RSYNC_TIMEOUT=600s` backstop prevents a true hang, so this is
latent rather than a confirmed hang. The preceding `ssh ... mkdir -p` call
correctly uses `SSH_OPTS` (line 196), making the omission inconsistent.

**Fix:** pass `-e "ssh {' '.join(SSH_OPTS)}"` to both rsync calls.

### 3.5 NEW · LOW · C1 — `ingest/main_retry.py` always returns 0

**File:** `ingest/main_retry.py` · Line 417

`_run()` always returns `0` at line 417 regardless of success/failure ratio:

```python
_log.info(
    "DONE | candidates=%d downloaded=%d timeout=%d gone=%d other=%d db=%d in %.0fs",
    stats.candidates, stats.downloaded, ...
)
return 0   # ← C1: no exit_status() equivalent
```

A run where 100% of downloads timed out exits 0. The log line contains the true
numbers, so a human reading logs would notice, but a cron/CI wrapper treating the
exit code as health would not.

Impact is Low (manually invoked, not a background daemon) but inconsistent with
the `loop_hardening.exit_status` contract.

**Fix:** return nonzero when `stats.downloaded == 0` and `stats.candidates > 0`,
or call an `exit_status()`-equivalent.
