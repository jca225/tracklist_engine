## 3. Open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` dishonest exit code (loop mode)

**File:** `analysis/gpu_worker.py` · Lines 359–372

**Class:** C — C3 (honest counting) + C1 (honest exit code).

`n_done` is incremented on the failure path as well as the success path. Both
terminal exit sites return 0 without calling `exit_status()`:

```python
# failure path — line ~364
failed_tids.add(track_audio_id)
n_done += 1        # ← C3: done counter advanced on failure
continue

# drain exit — line ~337
return 0           # ← C1: no exit_status(); always 0

# --max-tracks exit — line ~372
return 0           # ← C1: same
```

A GPU run where every track is a poison pill (all files corrupt, all DB writes
fail) exits with code 0 and logs "no unanalyzed tracks remain". CI/cron treats
it as success. Compare: `mac_analyze_loop.py` calls
`exit_status(n_done, n_failed)` from `loop_hardening`, which escalates to
nonzero+ERROR when failure ratio exceeds 50% or nothing succeeded.

**Fix:** separate `n_failed` counter (don't increment `n_done` on failure);
call `loop_hardening.exit_status(n_done, n_failed)` at both return sites.

**Carried since:** 2026-07-27. **Fix before next GPU box run.**

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` sha256_file call missing OSError guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # ← no try/except OSError
    if local_sha != asset.sha256:
```

The sibling backfill loops (now deleted) had this guard:
```python
try:
    local_sha = sha256_file(local_audio)
except OSError as exc:
    local_sha = f"<unreadable: {exc}>"
```

An `OSError` (e.g. rsync exited 0 but the file is unreadable or truncated)
would propagate uncaught into the main-loop `try` block, bypassing
`persist_failed_inc()` — the Counts tally undercounts failures.

**Fix:** wrap with `try/except OSError` and treat as transient (call
`register_transient`).

### 3.3 LOW (carried) · C3 — `mac_analyze_loop.py _persist_in_bg` exception scope too narrow

**File:** `scripts/mac_analyze_loop.py` · Lines ~419–422

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

`_persist_in_bg` catches only `subprocess.CalledProcessError`. An `OSError`
(scratch DB path missing after orphan cleanup) or
`sqlite3.OperationalError` (lock timeout on the local scratch write) would
terminate the background thread silently without calling `persist_failed_inc()`,
causing the Counts tally to undercount persist failures.

**Fix:** widen the except to `Exception`, log it, and still call
`persist_failed_inc()`.

### 3.4 LOW (new) · B1 — `mac_analyze_loop.py` rsync calls don't propagate SSH_OPTS

**File:** `scripts/mac_analyze_loop.py` · Lines 178–188 (`rsync_in`),
195–203 (`rsync_stems_out`)

`SSH_OPTS` provides `ConnectTimeout=15`, `ServerAliveInterval=15`, and
`BatchMode=yes`. Direct `subprocess.run(["ssh", *SSH_OPTS, ...])` calls
throughout the file apply these correctly. However, the rsync calls invoke
rsync without `-e "ssh {SSH_OPTS}"`, so rsync's underlying SSH session
does **not** inherit these settings:

```python
subprocess.check_call(
    ["rsync", "-q", "--timeout", str(RSYNC_IO_TIMEOUT),
     f"{PI_HOST}:{shlex.quote(remote)}", str(local)],
    timeout=RSYNC_TIMEOUT,   # subprocess wall-clock backstop
)
```

Without `ServerAliveInterval`, a dead-but-established Tailscale SSH
connection is not detected at the SSH level; rsync relies on the OS TCP
keepalive (often hours) or a data stall to notice. Without `BatchMode=yes`,
a missing key in a new environment could block waiting for a password prompt
instead of failing immediately.

**Mitigating factors:** `--timeout=RSYNC_IO_TIMEOUT` (300s I/O stall backstop)
and `timeout=RSYNC_TIMEOUT` (600s subprocess wall-clock backstop). These
prevent an infinite hang — the failure mode is a 600s delay rather than a
true wedge.

**Fix:** add `-e "ssh {' '.join(SSH_OPTS)}"` to both rsync invocations
(or equivalently use `shlex.join`). Low severity because the subprocess
timeout is a functional backstop.
