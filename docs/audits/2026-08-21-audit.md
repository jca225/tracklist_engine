### 2.1 NEW findings this week

#### [LOW] B — `mac_analyze_loop.py:_set_filter_clause()`: SQL/shell injection via `--set-ids`

**File:** `scripts/mac_analyze_loop.py` · Lines 107–113, 94–104 (`ssh_pi`)

**Class:** B (integrity) / latent hardening.

`_set_filter_clause()` builds a SQL fragment by string-interpolating
user-supplied `--set-ids` values with single-quote wrapping but without
single-quote escaping:

```python
def _set_filter_clause(set_ids: tuple[str, ...] | None) -> str:
    csv = ",".join(f"'{s}'" for s in ids)   # ← no .replace("'", "''")
    return "AND ta.track_id IN (SELECT DISTINCT track_id "
           f"FROM set_track_slots WHERE set_id IN ({csv})) "
```

This SQL string is then embedded inside a double-quoted shell argument and piped
over SSH in `ssh_pi()`:

```python
full = f'sqlite3 -separator "|" {CANONICAL_DB} "{sql}"'
subprocess.run(["ssh", *SSH_OPTS, PI_HOST, full], ...)
```

A `--set-ids` value containing a single quote (e.g. `' OR '1'='1`) or a double
quote would inject SQL into, or break the quoting of, the remote shell command.

In practice the risk is low: this is an internal CLI, `--set-ids` is always a
short alphanumeric slug (e.g. `w1mgcjt`), and the attacker would already have
local shell access. However, the pattern is inconsistent — `gpu_worker.py`'s
`_next_unanalyzed()` uses parameterised sqlite3 queries for the same filter —
and could bite if `--set-ids` is ever driven from external input or a config
file.

**Fix:** either (a) add `s.replace("'", "''")` in `_set_filter_clause` and
`shlex.quote` the outer shell argument in `ssh_pi`, or (b) use
`sqlite3`-over-ssh with parameterised ATTACH + query instead of embedding SQL
in the command string. (The gpu_worker pattern is the reference.)

**Grade:** Low · latent/hardening · confirmed present.

#### [LOW] B — `mac_analyze_loop.py:442`: local scratch audio hardcoded `.m4a` extension

**File:** `scripts/mac_analyze_loop.py` · Line 442

**Class:** B (integrity) / latent.

```python
local_audio = LOCAL_AUDIO / f"{tid}.m4a"  # ← extension hardcoded
rsync_in(remote_path, local_audio)         # copies actual file (may be .flac, .mp3, ...)
```

The local scratch path is always `<tid>.m4a` regardless of the format of the
remote file. rsync copies the file correctly, but the local name has the wrong
extension when the canonical `track_audio.path` ends in `.flac`, `.mp3`, or
other formats. Most audio libraries (`soundfile`, `librosa`) probe the file
header and are extension-agnostic, so analysis nearly always succeeds anyway.
The file is unlinked after use, so no permanent damage occurs. However, if any
adapter or library path branches on extension, it would silently misidentify
the format.

**Fix:** derive the extension from `remote_path` — e.g.
`local_audio = LOCAL_AUDIO / f"{tid}{Path(remote_path).suffix or '.m4a'}"`.

**Grade:** Low · latent · confirmed present.
