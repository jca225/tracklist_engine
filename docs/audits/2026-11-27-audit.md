### Findings

#### Medium — Latent hardening gap (not a Blocker/High)

**M1 · `rsync_stems_out` lacks post-push integrity verification**  
*File:* `scripts/mac_analyze_loop.py:191–203`  
*Class:* B (integrity check)  
*Status:* Latent / hardening gap

The pull path (`rsync_in`) is guarded by a sha256 check after transfer (`sha256_file` in `loop_hardening.py`, called at line ~455). The push path (`rsync_stems_out`) uses correct SSH_OPTS, `--timeout`, and subprocess wall-clock timeout — so B1 (hang) is covered — but there is no post-push checksum to confirm what arrived on pi-storage matches what was sent. A silent disk-write failure on pi-storage after rsync reports success would leave a truncated or corrupt stem as canonical.

In practice rsync is reliable, and stems can be regenerated from source audio. Grade: **Medium / latent** — no known occurrence, no data loss risk on the analysis path itself.

#### Low — Latent (already in entropy fence)

**L1 · `_probe_duration_s` uses `text=True` without explicit `encoding`**  
*File:* `scripts/replace_track_audio.py:643–654`  
*Class:* A (encoding)  
*Status:* Latent; already counted in `net_subprocess_no_encoding` fence (8 remaining)

`subprocess.run([ffprobe, ...], text=True)` does not specify `encoding="utf-8"`. On pi-storage's Latin-1 locale, ffprobe `format=duration` output is pure ASCII (floating-point seconds), so there is no actual mojibake path here. The fix is cosmetic: add `encoding="utf-8", errors="surrogateescape"` per `loop_hardening.TEXT_KW`. Grade: **Low / latent**.

#### Low — By design (informational)

**L2 · `ingest/main.py` and `ingest/main_retry.py` always exit 0**  
*Files:* `ingest/main.py:617`, `ingest/main_retry.py:417`  
*Class:* C1 (exit-code honesty)  
*Status:* By design; not covered by `loop_hardening.exit_status`

Both ingest entrypoints return `0` unconditionally. `loop_hardening.exit_status` applies only to the analysis loops (mac_analyze_loop, gpu_worker), not to the idempotent download crawlers. For a dominated-failure run (say, 90% of tracks fail to download), systemd/CI sees success. This is acceptable for crawlers — download failures are common and expected, and re-running is idempotent — but means monitoring dashboards cannot distinguish "drained cleanly" from "drained with all failures." Not a regression; noted for awareness. Grade: **Low / by design**.
