### 2.2 New finding (MEDIUM latent) — `gpu_worker.py` loop-mode: no `busy_timeout` on `_next_unanalyzed`

**File:** `analysis/gpu_worker.py` · Lines ~158–197

**Class:** B (missing hardening) / C1 (honest exit code on lock contention).

**Grade:** MEDIUM latent.

`_next_unanalyzed` uses `sqlite3.connect(db_path)` with no `timeout` argument
(SQLite default: 5 s). When the canonical DB is held by a concurrent pi-storage
writer for longer than 5 s, `sqlite3.DatabaseError: database is locked` propagates
through the `except sqlite3.DatabaseError` catch, returns `Err(...)`, and the
caller at `_run()` does:

```python
nxt = _next_unanalyzed(args.db, set_filter, frozenset(failed_tids))
if not nxt.is_ok():
    _log.error(nxt.error)
    return 1           # ← kills the entire loop
```

A momentary write lock (the pi scraper, a replace_track_audio call) would abort
a multi-hour GPU analysis loop with exit code 1 rather than waiting up to
`busy_timeout` and retrying. Compare: `mac_analyze_loop.py push_track_rows` adds
`PRAGMA busy_timeout=120000;` in the same transaction (fixed 2026-07-17).

The fix is one line: `sqlite3.connect(db_path, timeout=120.0)` in
`_next_unanalyzed` (or move to `core.db.connect` which already enforces FK).
This finding is MEDIUM because it only fires when a concurrent writer holds the
lock for >5 s, which is unusual but possible during heavy ingest sessions.

*Not carried to the rolling issue as Blocker/High — grade is MEDIUM. Included
here as a new finding for the record. Will add to issue #8 as MEDIUM.*
