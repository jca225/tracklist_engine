### 2.1 HIGH — Family B/C — `scripts/mac_analyze_loop.py` — TimeoutExpired not caught in main loop (NEW)

**Confirmed.**

`ssh_pi()` (line ~93) calls `subprocess.run(..., timeout=SSH_QUERY_TIMEOUT)`, and
`rsync_in()` (line ~171) calls `subprocess.check_call(..., timeout=RSYNC_TIMEOUT)`.
Both raise `subprocess.TimeoutExpired` on a hung SSH/rsync call.

`TimeoutExpired` and `CalledProcessError` are **sibling** classes under
`subprocess.SubprocessError`; catching one does not catch the other.

The main `while True:` loop has two exposure points:

1. `nxt = next_task(...)` is called **outside** the try/except block (line ~426).
   `next_task` calls `ssh_pi`, which can raise `TimeoutExpired`. The exception
   propagates uncaught and kills the entire analysis loop process.

2. The `except subprocess.CalledProcessError` handler (line ~517) handles the
   timeout comment `# timeout, broken pipe, etc.` but does not actually catch
   `TimeoutExpired`. Same gap in `_persist_in_bg` background thread (line ~419).

**Failure scenario:** a pi-storage SSH session hangs (network partition, load spike,
Tailscale reconnect). `ssh_pi` fires after `SSH_QUERY_TIMEOUT=120 s`, raises
`TimeoutExpired`. The exception either propagates uncaught from `next_task` (crash)
or exits the inner try block with an unhandled exception. In both cases the entire
Mac analysis loop process terminates. On a 200–250 s/track run it can silently kill
hours of analysis progress with no ledgered failure.

**Fix:** change both `except subprocess.CalledProcessError` handlers to
`except (subprocess.CalledProcessError, subprocess.TimeoutExpired)`, and move the
`next_task(...)` call inside the try block (or wrap it in its own narrow try).

### 2.2 MEDIUM — Family C (C1 + C3) — `analysis/gpu_worker.py` — n_done incremented on failure; always returns 0 (STILL OPEN from 2026-07-27)

**Confirmed still open.**

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: increments done on failure
    continue
...
n_done += 1
```

Both terminal paths (`queue drained` and `--max-tracks hit`) `return 0` regardless
of `len(failed_tids)`. Progress logs show `n_done` as if failures are successes.
Callers (cron, gpubox orchestrator) cannot distinguish a run with 100% failures from
a clean run.

**Fix:** honour `failed_tids` in the return code (e.g. non-zero when failure ratio
exceeds threshold), and remove `n_done += 1` from the failure path.

### 2.3 LOW — Family B — `scripts/mac_analyze_loop.py` — sha256_file OSError not caught (STILL OPEN from 2026-07-27 §3.2)

**Confirmed still open.**

`sha256_file(local_audio)` (line ~454) can raise `OSError` if the just-downloaded
file is missing or unreadable (partial rsync, disk full). The surrounding try block
catches only `subprocess.CalledProcessError`, so an `OSError` here propagates up,
potentially killing the loop on a one-off file system event.

**Fix:** broaden the integrity-check block to also catch `OSError`, or add a
`local_audio.exists()` guard before calling `sha256_file`.

---

### 2.4 LOW — Family C — `scripts/mac_analyze_loop.py` — `_persist_in_bg` catches only CalledProcessError (STILL OPEN from 2026-07-27 §3.4)

**Confirmed still open.** Same gap as 2.1 but scoped to the background persist
thread rather than the main loop. `_persist_in_bg` calls `ssh_pi` and its
`except subprocess.CalledProcessError` handler misses `TimeoutExpired`. A hung SSH
inside the background thread raises an unhandled exception, which terminates the
daemon thread and silently stops all background persistence for the rest of the run.

This is partially subsumed by 2.1 (fixing the main loop handler covers the pattern),
but the thread has its own independent handler that also needs patching.
