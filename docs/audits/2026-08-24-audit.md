## 3. Open findings

### 3.1 HIGH (new) · B1 — `mac_analyze_loop.py` main loop crashes on rsync timeout instead of quarantining

**File:** `scripts/mac_analyze_loop.py` · Line 517 (main loop's `except`
around the pull/analyze/dispatch body).

**Class:** B1 (unbounded network call) + C2 (transient-vs-poison mishandling).

`rsync_in` (line 171) and its callers use
`subprocess.check_call([...], timeout=RSYNC_TIMEOUT)`. When rsync stalls
(broken Tailscale pipe, long dead I/O) `subprocess.run/check_call` raises
**`subprocess.TimeoutExpired`**, which is **not a subclass of
`CalledProcessError`** — both inherit from `SubprocessError`, siblings. The
main loop only catches:

```python
except subprocess.CalledProcessError as e:
    # Pull/ssh failures reaching here are transient (timeout, broken
    # pipe) — retry with backoff before quarantining (C2).
    if register_transient(tid, str(e), attempts, failed_tids, counts, log):
        n_seen += 1
```

The comment on lines 518–519 **assumes** the timeout path is caught here.
It is not. A rsync stall past `RSYNC_TIMEOUT` (600s) propagates out through
this except → `finally` (which unlinks `local_audio`) → out of the
`while True` → **loop process exits** with the exception. Consequences:

- The retry-with-backoff (`register_transient` + `transient_backoff_seconds`)
  never runs — the very class of failure `loop_hardening.py` was built to
  survive.
- One flaky tid takes down the whole drain; the systemd unit / tmux
  wrapper has to notice and relaunch.
- `exit_status()` never fires — no honest failure summary.

**Failure scenario:** stale Tailscale route to `pi-storage` mid-drain; one
`rsync -q --timeout 300 pi-storage:… local` hangs past 600s → `TimeoutExpired`
uncaught → analyze loop dies with 30 tracks still queued.

**Fix (one line):**
```python
except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:
```
(or `except subprocess.SubprocessError as e:`).

**Confirmed present** on `main` at c59565f. **Not covered by loop_hardening.py**
— the centralized primitives export timeout constants and helpers but the
call-site `except` clause is per-loop and this one still filters the wrong
type.

### 3.2 MEDIUM (extends 3.4/2026-07-27) · C3 — `_persist_in_bg` also silently drops rsync/SSH push timeouts

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424 (the background
persist thread `_persist_in_bg`).

**Class:** C3 (dishonest counting).

Same root cause as 3.1, different consequence class. The bg thread runs
`rsync_stems_out` (line 191, `timeout=RSYNC_TIMEOUT`) and `push_track_rows`
(line 236, `timeout=SSH_PUSH_TIMEOUT`) and catches only
`subprocess.CalledProcessError`:

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

When those pushes exceed their wall-clock timeout, `TimeoutExpired`
propagates out through the try, past the `finally` that cleans `stem_local`,
and terminates the background thread with an unhandled exception. Net
effect: `n_seen` was already incremented at hand-off, but neither
`counts.done_inc()` nor `counts.persist_failed_inc()` runs. The tally
under-reports the failure and the exit_status heuristic (`n_failed / total`)
looks better than reality.

The 2026-07-27 audit (3.4) flagged the same too-narrow `except` clause but
enumerated `OSError` / `sqlite3.OperationalError` as the missed exceptions —
`subprocess.TimeoutExpired` was not called out. Timeout is the exception
this code will actually see because both push paths use `timeout=` (and
those timeouts are set precisely so a slow pi can't wedge the loop). This
elevates the prior finding from LOW to Medium.

**Fix:** same shape as 3.1 — widen the `except` (and re-log
persist_failed_inc for `TimeoutExpired`).

### 3.3 MEDIUM (carried from 2026-07-27 §3.1) · C1+C3 — `gpu_worker.py` loop always returns 0

**File:** `analysis/gpu_worker.py` · Lines 326–372.

Same finding as 2026-07-27 §3.1; still open on `main`. `n_done` is
incremented on the failure branch (line 364) and both terminal returns
(line 337, line 372) are unconditional `return 0`. A drain where every
track fails logs "no unanalyzed tracks remain — done (processed N,
quarantined N)" and exits 0. No `exit_status()` call. Fix from the prior
audit still applies: increment `n_failed` on the failure path and route
both returns through `exit_status(n_done, n_failed)`.

### 3.4 LOW (new, latent) · B1 — `ingest/adapters/downloader.py` yt-dlp API calls have no wallclock backstop

**File:** `ingest/adapters/downloader.py` · Lines 104–121 (`download_one`) and
Lines 162–179 (`download_set_mix`).

Both call `YoutubeDL.extract_info(...)` on the Python API path. Only
`retries=cfg.retries` is passed; no `socket_timeout`, no external wallclock.
`ingest.main` is a long-running background loop that processes ~16k tracks;
a yt-dlp extract call stuck in a `read()` on a slow upstream stalls the
whole ingest thread. Sibling adapters (`ytmusic_adapter.py:216`,
`spotdl_adapter.py:99,232`, `stem_guard_runner.py:26`) all bound the
outward-call via `subprocess.run(..., timeout=…)` + explicit
`TimeoutExpired` handling; the Python-API path here has neither.

Latent because yt-dlp does honor OS-level socket defaults, so a fully-idle
socket eventually errors out — but a slow-drip malicious/misbehaving
extractor can hold the thread for tens of minutes. Fix suggestion: add
`socket_timeout` to `_ydl_opts` (e.g. 60s) and, if `ingest.main` needs a
hard backstop, wrap `extract_info` in a bounded worker thread.
