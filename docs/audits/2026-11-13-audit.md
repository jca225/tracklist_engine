## 3. Open findings

### 3.1 HIGH (new) · B1 / C2 — `mac_analyze_loop.py` main loop crashes on `subprocess.TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Lines 93–104, 116–142, 426–530

**Class:** B (missing timeout guard) + C2 (transient vs poison — a timeout is
transient but causes a crash instead of a retry).

The main `while True:` loop in `main()` calls `next_task()` **outside** the
`try/except` block, and the inner `try` only catches
`subprocess.CalledProcessError`:

```python
# Line 431 — OUTSIDE the try block:
nxt = next_task(frozenset(failed_tids), set_ids=set_ids, ...)

# Lines 445–530 — inner try/except:
try:
    rsync_in(remote_path, local_audio)      # subprocess.check_call, timeout=600
    asset = fetch_asset(tid, local_audio)   # calls ssh_pi, timeout=120
    ...
except subprocess.CalledProcessError as e:   # ← TimeoutExpired is NOT caught
    if register_transient(tid, str(e), ...):
        ...
```

`next_task()` calls `ssh_pi()`, which uses `subprocess.run(..., timeout=SSH_QUERY_TIMEOUT=120)`.
When pi-storage is under concurrent write load (the pi services, another loop,
or a USB-write stall), a `sqlite3` query can exceed 120s even with
`PRAGMA busy_timeout`. When it does, `subprocess.TimeoutExpired` propagates out
of `next_task()` — which is **outside** the try block — and crashes `main()`
with an unhandled exception, requiring a manual restart.

The same gap exists for `rsync_in()` and `fetch_asset()` inside the try block:
`TimeoutExpired` is a sibling of `CalledProcessError` (both inherit from
`subprocess.SubprocessError`), so it escapes the existing `except
CalledProcessError` and crashes the loop.

**Impact:** The whole analysis session dies rather than retrying the timed-out
SSH call with backoff. `register_transient` / `transient_backoff_seconds` from
`loop_hardening.py` are never reached for timeout failures, defeating the C2
transient-retry intent. A single DB-lock or Tailscale hiccup during a 36-hour
Mac run kills the session.

**Fix:** Broaden the outer `except` clause and wrap `next_task()`:

```python
# Option A — widen the existing catch (also covers _persist_in_bg, 3.2):
except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:
    ...

# AND guard next_task() — move it inside the try block, or add its own:
try:
    nxt = next_task(frozenset(failed_tids), ...)
except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:
    # treat as transient; backoff and retry
    time.sleep(transient_backoff_seconds(attempts.get(0, 0)))
    continue
```

### 3.2 HIGH (carried from 2026-11-11) · C2 / C3 — `_persist_in_bg` catches only `CalledProcessError`; `TimeoutExpired` escapes silently

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424

```python
def _persist_in_bg(tid: int, stem_local: Path) -> None:
    try:
        ...
        rsync_stems_out(stem_local, tid)   # subprocess.check_call, timeout=600
        push_track_rows(tid)               # subprocess.run, timeout=SSH_PUSH_TIMEOUT=300
        counts.done_inc()
    except subprocess.CalledProcessError as e:   # ← TimeoutExpired NOT caught
        counts.persist_failed_inc()
        log.error("[%d] (bg) push failed: %s", tid, e)
    finally:
        shutil.rmtree(stem_local, ...)
```

If `rsync_stems_out` or `push_track_rows` raises `subprocess.TimeoutExpired`,
it escapes the `except` clause. Python's default thread exception handler prints
to stderr but neither `done_inc()` nor `persist_failed_inc()` is called. The
track appears as "dispatched" (`n_seen++`) with no accounting entry in
`counts` — when the queue drains, `exit_status(done=0, failed=0)` sees no
work and returns 0 (clean drain) even though analysis results were never
pushed to canonical.

**Fix:** `except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:`
(or `except subprocess.SubprocessError`). Same root cause as 3.1.

### 3.3 MEDIUM (carried from 2026-07-27) · C1+C3 — `gpu_worker.py` loop mode increments `n_done` on failure and always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~350–372

```python
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", ...)
    failed_tids.add(track_audio_id)
    n_done += 1    # ← advances on failure
    continue
n_done += 1        # ← also advances on success

# ...
_log.info("no unanalyzed tracks remain — done (processed %d, quarantined %d)", ...)
return 0           # ← always returns 0
```

A session where every track fails returns 0 and logs "done" with n quarantined.
CI/cron treats this as success. `mac_analyze_loop.py` calls
`exit_status(n_done, n_failed)` from `loop_hardening` which escalates to
nonzero+ERROR when `n_done == 0`; `gpu_worker.py` has no equivalent.

**Fix:** separate `n_done` (successes) from `n_failed` (failures), and call
`exit_status(n_done, n_failed)` from `loop_hardening` at both drain-return sites.
