### Class C1 — Silent-failure loops / dishonest exit codes

#### [MEDIUM — confirmed present] `analysis/gpu_worker.py` — loop mode exits 0 on all-failure run

**Location:** `analysis/gpu_worker.py:326–372` (`_run`, loop branch)

**Description:** In `--loop` mode, tracks that fail `_process_one` are added to `failed_tids` and the loop continues. When the queue is fully drained (all failing tracks excluded by `failed_tids`), `_next_unanalyzed` returns `Ok(None)` and the function returns `0` with the message `"no unanalyzed tracks remain"` — identical to a fully-successful run. `loop_hardening.exit_status()` exists precisely for this class but is not imported by `gpu_worker.py`.

**Failure scenario:** gpubox run against a mounted directory that unmounts mid-run (`sshfs` drop, Tailscale outage) — every `_process_one` call returns `Err("audio file missing")`, all N tracks go to `failed_tids`, loop drains cleanly, process exits 0. The orchestrator logs success; N tracks remain unanalyzed with no alert.

**Also:** `n_done` at line 364 is incremented for *failed* tracks too (inside the `if not r.is_ok()` branch), so `--max-tracks` stops after N *attempts*, not N *successes*. This conflates failure and success in the headline counter (low-priority sub-finding).

**Not a blocker** because gpubox jobs have manual log review; no automated alert path reads the exit code today. Would become a blocker if an orchestrator ever gates re-runs on exit code.

#### [MEDIUM — confirmed present] `ingest/main_retry.py` — exits 0 regardless of DB failures

**Location:** `ingest/main_retry.py:411–417` (`_run`, bottom of function)

**Description:** `_run()` returns `return 0` unconditionally at line 417. The function correctly logs `db_failed`, `failed_timeout`, `failed_other`, etc. into `RunStats`, but those stats are only written to the log — the exit code is always 0. A run in which every `insert_audio_or_reap` call fails (DB locked during migration, schema drift) looks identical to a fully-successful spotdl pass.

**Failure scenario:** spotdl retry pass during a DB migration — 50 downloads succeed, all 50 inserts fail with `SQLITE_BUSY`/`DatabaseError`. `stats.downloaded == 0`, `stats.db_failed == 50`. Orchestrator sees exit 0 and marks the tracks as handled; they remain absent from `track_audio` indefinitely.

**Note:** `stats.downloaded` and `stats.db_failed` are both printed at INFO level at the end, so the failure is visible to anyone watching the log. The issue is that *automated* retrigger or CI monitoring can't detect it.

### Code quality / substrate (Low / latent)

#### [LOW — latent] `analysis/gpu_worker.py` — direct `sqlite3` import violates substrate rule

**Location:** `analysis/gpu_worker.py:159, 205` (`_next_unanalyzed`, `_load_audio_asset`)

**Description:** Both helpers use `sqlite3.connect` directly, bypassing `core.db.connect`. As a result, FK enforcement (`PRAGMA foreign_keys = ON`) is never set on these connections, and `row_factory` is not applied (columns accessed by index — fragile to schema column reordering). CLAUDE.md explicitly states "Domain code never imports `sqlite3` directly." Since both functions are read-only today, the correctness impact is nil; the latent risk is a future write being added without FK protection.
