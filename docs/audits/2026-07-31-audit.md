## 3. Findings this run

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py`: `n_done` incremented on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines 359–372  
**Class:** C (silent-failure loop) — C1 honest exit + C3 honest counting.

`n_done` is incremented on both the failure path (line 364) and success path
(line 369):

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: done counter advanced on failure
    continue
...
n_done += 1
```

Both terminal exit paths return 0 unconditionally:
- **Drain path** (line 337): `return 0` — a session where all tracks fail
  logs "done (processed 0, quarantined N)" and exits successfully.
- **`--max-tracks` path** (line 372): `return 0` — after N total attempts
  (successes + failures), exits 0 even if zero tracks were analyzed.

Compare: `mac_analyze_loop.py` imports and calls `exit_status(done, failed, pf)`
from `loop_hardening`, which escalates to nonzero+ERROR when `n_done == 0` or
failure ratio exceeds the limit.

**Fix:** Track `n_failed` separately; call `exit_status(n_done, n_failed)` at
both return sites. Match the `loop_hardening` contract.

### 3.2 LOW (carried) · B2 — `mac_analyze_loop.py:459` `sha256_file` without `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Line 459

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # ← no try/except OSError
    if local_sha != asset.sha256:
```

An `OSError` here propagates uncaught through the main `try` block into the
outer `except subprocess.CalledProcessError` — which does NOT catch it —
so the exception bubbles all the way out of the `while True` loop, crashing
the process entirely. This is worse than the issue number suggests.

The backfill loops (absent from this checkout) had the guard:
```python
try:
    local_sha = sha256_file(local_audio)
except OSError as exc:
    local_sha = f"<unreadable: {exc}>"
```

An `OSError` after a successful rsync is extremely rare (would require the
file to become unreadable between rsync exit and the open in `sha256_file`),
but when it hits, the whole analysis loop crashes rather than quarantining the
one bad track.

**Fix:** Wrap `sha256_file(local_audio)` in `try/except OSError` and treat it
as a transient pull failure (same as sha256 mismatch — call
`register_transient`).

### 3.3 LOW (carried) · C3 — `mac_analyze_loop._persist_in_bg` catches only `CalledProcessError`

**File:** `scripts/mac_analyze_loop.py` · Lines 419–424

```python
try:
    ...
    rsync_stems_out(stem_local, tid)
    push_track_rows(tid)
    counts.done_inc()
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

`push_track_rows` opens two local sqlite3 connections (lines 261, 323 in the
function). A `sqlite3.OperationalError` (DB locked, disk full, corrupted
scratch) or `OSError` (scratch path missing) would propagate uncaught past the
`except` clause, silently killing the background thread. Consequences:

1. `persist_failed_inc()` is never called — the Counts tally under-reports
   persist failures.
2. `done_inc()` is never called — the track remains in the scratch DB and
   may leak scratch rows.
3. The main loop's `exit_status()` call sees cleaner counts than reality.

**Fix:** Broaden to `except Exception` with `log.exception`; always call
`persist_failed_inc()` on any non-`CalledProcessError` exception.

### 3.6 LOW (new) · C1 — `ingest/main.py` and `ingest/main_retry.py` always exit 0

**Files:** `ingest/main.py:617`, `ingest/main_retry.py:417`

Both `_run()` functions return 0 unconditionally at the end of a run,
regardless of failure count. `_summarize()` (main.py) and the final `_log.info`
(main_retry.py) print failure counts to stderr, but the exit code is always
success.

This means a cron job that runs `ingest.main` and observes exit code will
never be alerted even if every track download failed (for example, after a
full yt-dlp bot-detection lockout). The counters exist (`stats.failed_download`
/ `stats.db_failed`), so the fix is a simple gate.

Graded **Low** (not Medium) because: (a) these are intentional bulk pipelines
where partial success is expected design, (b) failures are always logged
individually, and (c) a total-failure scenario would be caught by external
monitoring (empty `track_audio` table growth). Marking latent.
