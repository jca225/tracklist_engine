## 3. Open findings

### 3.1 MEDIUM · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~359–372

**Class:** C (silent-failure loop) — C3 honest-counting + C1 honest exit code.

`n_done` is incremented on both success and failure paths:

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: done counter advanced on failure
    continue
_log.info("OK [%d] ...", n_done + 1, ...)
n_done += 1
```

The loop exits via `return 0` at both terminal conditions (queue drained and
`--max-tracks` hit) without calling `exit_status()`. Consequences:

1. A session where every track fails logs "done" and returns 0 — CI/cron treats
   it as success. Compare: `mac_analyze_loop.py` calls `exit_status(n_done,
   n_failed)` which escalates to nonzero+ERROR when `n_done == 0` or failure
   ratio is high.
2. `--max-tracks N` is driven by `n_done`. Ten consecutive failures with
   `--max-tracks=10` exhaust the limit without ever successfully analyzing a
   track; the caller receives exit 0 and no records written.

**Fix:** increment `n_failed` (not `n_done`) on the failure path; call
`exit_status(n_done, n_failed)` at both return sites instead of `return 0`.
This matches the `loop_hardening.exit_status` contract already used by
`mac_analyze_loop.py`.

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

`set_mert_backfill_loop.py` has the identical pattern with the guard:

```python
try:
    local_sha = sha256_file(local_audio)
except OSError as exc:
    local_sha = f"<unreadable: {exc}>"
```

An `OSError` here would propagate uncaught, killing the analysis thread for
that track and leaving `persist_failed_inc()` uncalled. Impact: low (rsync
would have to exit 0 and then the file becomes unreadable in the same window),
but the inconsistency is a latent B-class gap.

### 3.3 LOW (carried) · C2 — backfill loops quarantine on first `CalledProcessError`, no bounded retry

**Files:** `scripts/mert_backfill_loop.py`, `scripts/set_mert_backfill_loop.py`

Neither imports `register_transient` from `loop_hardening`. A transient SSH or
rsync failure (network blip, pi busy) causes immediate quarantine into the
skip-set for the rest of the session. `mac_analyze_loop.py` uses
`register_transient` with `MAX_TRANSIENT_ATTEMPTS=3` + exponential backoff
before promoting to the permanent skip-set.

Impact: low per-session (just wastes a slot and re-queues next session), but
a flaky Tailscale moment quietly inflates failure counts in logs.

---

### 3.4 LOW (carried) · C3 — `mac_analyze_loop.py _persist_in_bg` catches only `CalledProcessError`

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424

`_persist_in_bg` only catches `subprocess.CalledProcessError`. An `OSError`
(scratch DB path missing) or `sqlite3.OperationalError` (lock timeout on
scratch write) would terminate the background thread silently without calling
`persist_failed_inc()` — the Counts tally would undercount failures.

### 3.5 LOW (new) · B — `set_mert_backfill_loop.push_set_mert_rows` splits one logical write across two SSH transactions

**File:** `scripts/set_mert_backfill_loop.py` · Lines ~193–254

`push_set_mert_rows` issues the `set_mert_measures` INSERT in one `BEGIN
IMMEDIATE` transaction and the `set_analysis.analyzer_versions_json` UPDATE in
a separate SSH call:

```python
# Transaction 1 (correct — BEGIN IMMEDIATE)
subprocess.run(["ssh", ..., f"sqlite3 {CANONICAL_DB}"], input="\n".join(sql_lines), ...)

# Gap: separate query to read current versions_json
versions_raw = ssh_pi("SELECT analyzer_versions_json ...")

# Transaction 2 (separate — no BEGIN IMMEDIATE, no .bail on)
subprocess.run(["ssh", ..., f"sqlite3 {CANONICAL_DB}"],
    input=f"UPDATE set_analysis SET analyzer_versions_json=...", ...)
```

`mert_backfill_loop.push_mert_rows` does both in a single `BEGIN IMMEDIATE`
transaction. If the second SSH call fails, `set_mert_measures` rows exist but
`analyzer_versions_json` is stale — the set would be re-embedded on the next
run (satisfies queue predicate `dim=1024` already, so it actually won't be
re-queued — the version metadata just stays wrong permanently). Low severity
because the duplicate-guard is on `set_mert_measures`, not on the version field.
