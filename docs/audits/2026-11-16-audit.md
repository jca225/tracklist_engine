## 3. Open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~359–372 · **Confirmed present.**

`n_done` is incremented on both success and failure paths:

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: done counter advanced on failure
    continue
_log.info("OK [%d] ...", n_done + 1, ...)
n_done += 1
```

Both terminal conditions (`return 0` at line 337 and 372) return 0 without
calling `exit_status()`. Consequences:

1. A session where every track fails logs "done" and returns 0 — CI/cron
   treats it as success.
2. `--max-tracks N` is driven by `n_done`. Ten consecutive failures with
   `--max-tracks=10` exhaust the limit without analyzing a single track;
   caller receives exit 0 and no rows written.

**Fix:** increment `n_failed` (not `n_done`) on the failure path; call
`exit_status(n_done, n_failed)` at both return sites. Matches the pattern already
used by `mac_analyze_loop.py` (lines 438, 514).

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Line ~455 · **Confirmed present.**

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

An `OSError` here (file disappears between rsync finish and sha256_file call)
propagates uncaught out of the try block, kills the analysis thread for that
track, and leaves `persist_failed_inc()` uncalled. Consequence: Counts tally
underreports failures and the track is not quarantined.

Compare: `set_mert_backfill_loop.py` (now deleted) had the guard as a model
to follow.

### 3.3 LOW (carried) · C3 — `mac_analyze_loop.py _persist_in_bg` catches only `CalledProcessError`

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424 · **Confirmed present.**

```python
def _persist_in_bg(tid: int, stem_local: Path) -> None:
    try:
        ...
        push_track_rows(tid)
        counts.done_inc()
    except subprocess.CalledProcessError as e:
        counts.persist_failed_inc()
        log.error(...)
```

An `OSError` (scratch DB path missing) or `sqlite3.OperationalError` (lock
timeout on scratch write) would terminate the background thread silently
without calling `persist_failed_inc()`. The Counts tally then undercounts
failures, and the track appears as "in flight" indefinitely.

**Fix:** widen the except to `Exception` (or at minimum `(subprocess.CalledProcessError,
OSError, sqlite3.OperationalError)`) and call `persist_failed_inc()` in all
error paths.

### 3.4 LOW (new) · C1 — `ingest/main_retry.py` always returns 0 regardless of batch outcome

**File:** `ingest/main_retry.py` · Line 417 · **Confirmed present.**

```python
    _log.info(
        "DONE | candidates=%d downloaded=%d timeout=%d gone=%d other=%d db=%d in %.0fs",
        ...
    )
    return 0   # ← always 0, even when db_failed > 0 or downloaded == 0
```

The retry pass logs the full `RunStats` breakdown but always returns 0. A run
with `candidates=50, downloaded=0, db_failed=50` exits clean. Since this is a
targeted surgical retry (not the primary acquisition loop) and all failures are
logged at `ERROR`/`WARNING` level, the blast radius is low — a cron job or
Makefile rule driven by this exit code would just not notice failed DB writes.
Severity: LOW — the stats are plainly visible in the log, and re-running
cleans up.
