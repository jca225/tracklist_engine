## 2. Semantic findings

### Finding 1 — High · Confirmed present

**`mac_analyze_loop.py:_persist_in_bg` narrow-catch lets `TimeoutExpired` escape
silently, leaving counts unchanged → `exit_status` reads as clean success**

**Class C1 / C3** (dishonest exit code + dishonest counting)

`_persist_in_bg` (line 419) catches only `subprocess.CalledProcessError`:

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

Both `rsync_stems_out` and `push_track_rows` invoke `subprocess.check_call` /
`subprocess.run` with `timeout=RSYNC_TIMEOUT` (600 s) and `timeout=SSH_PUSH_TIMEOUT`
(300 s). Those bounded calls raise `subprocess.TimeoutExpired` on expiry.
`TimeoutExpired` inherits from `SubprocessError` — it is a **sibling**, not a
subclass, of `CalledProcessError`. So a timeout in the bg thread:

1. Escapes the `except` clause.
2. Runs the `finally` (stems dir cleaned up — good).
3. Exits the thread with an unhandled exception, printed to stderr.
4. Neither `counts.done_inc()` nor `counts.persist_failed_inc()` is called.
5. The main loop's `bg.join()` returns normally — there is no way to detect the
   failure at join time.

Consequence: if the pi-storage push times out on a track, `n_seen` was
incremented but all three counters (`done`, `failed`, `persist_failed`) remain
unchanged. `exit_status(0, 0, 0)` returns `(0, INFO, "queue drained — analyzed
0, failed 0")` — **reads as clean success while analysis work is silently lost**.
The DB row is never written; the track stays unanalyzed; the loop picks it up
again on the next run (not an infinite spin, since the loop restarts fresh) but
the operator sees no alarm.

**Failure scenario:** Tailscale degrades during a long analysis session;
`rsync_stems_out` or the sqlite3-over-ssh call in `push_track_rows` hits the
300–600 s wall-clock timeout. The session drain reads "done 0, failed 0 — queue
drained" in the log. The operator concludes the run was clean; in fact every
track that was handed off to the bg thread was lost.

**Fix:** broaden the except clause to cover `subprocess.SubprocessError` (the
common base of both `CalledProcessError` and `TimeoutExpired`), or catch both
explicitly:

```python
except subprocess.SubprocessError as e:   # catches CalledProcessError + TimeoutExpired
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

### Finding 2 — Medium · Latent / hardening

**`rsync_in` and `rsync_stems_out` don't pass SSH_OPTS to rsync's SSH
transport — no BatchMode, no keepalive on rsync connections**

**Class B1** (missing timeout hardening)

`loop_hardening.py` exports `SSH_OPTS` with `ConnectTimeout=15`,
`ServerAliveInterval=15`, `ServerAliveCountMax=3`, `BatchMode=yes`. The two
rsync helpers in `mac_analyze_loop.py` import and use the TIMEOUT CONSTANTS
from loop_hardening, but do not pass SSH_OPTS to rsync via `-e "ssh ..."`:

```python
subprocess.check_call(
    ["rsync", "-q", "--timeout", str(RSYNC_IO_TIMEOUT), f"{PI_HOST}:{remote}", str(local)],
    timeout=RSYNC_TIMEOUT,   # ← wall-clock backstop is present
)
```

Effects:
- **No `BatchMode=yes`**: if the SSH key is absent/expired, rsync hangs
  prompting for a password rather than failing fast; released only by the
  RSYNC_TIMEOUT (600 s) wall-clock.
- **No `ServerAliveInterval/Count`**: a silently dead Tailscale tunnel stalls
  rsync for the full 600 s instead of ~45 s with keepalives.

This is bounded (the wall-clock backstop fires) and not an infinite hang, so it
is latent/hardening rather than a blocker. But in the common Tailscale-glitch
scenario it burns 600 s per track instead of 45 s, and the missing BatchMode
introduces a password-prompt hang risk.

**Fix:** add `-e "ssh {' '.join(SSH_OPTS)}"` to both rsync invocations, or
factor both helpers to use a shared `RSYNC_SSH_CMD` constant built from
`SSH_OPTS`.
