### [MEDIUM / LATENT] B2 — MERT backfill loops missing post-rsync sha256 integrity check

**Files:** `scripts/mert_backfill_loop.py`, `scripts/set_mert_backfill_loop.py`
**Class:** B2 — no post-transfer integrity check

Both loops import from `loop_hardening` but omit `sha256_file`:

```python
# mert_backfill_loop.py / set_mert_backfill_loop.py — what IS imported
from scripts.loop_hardening import (
    RSYNC_IO_TIMEOUT, RSYNC_TIMEOUT, SSH_OPTS,
    SSH_PUSH_TIMEOUT, SSH_QUERY_TIMEOUT,
    exit_status,
)
# sha256_file, register_transient, transient_backoff_seconds — NOT imported
```

After `rsync_in()`, neither loop verifies the pulled audio against the
canonical `track_audio.sha256`. In contrast, `vast_loop.py` (lines 638–649)
and `mac_analyze_loop.py` (lines 454–464) both gate on sha256 before
proceeding:

```python
# vast_loop.py — reference pattern
if item.asset.sha256:
    local_sha = sha256_file(local_audio)
    if local_sha != item.asset.sha256:
        # treat as transient pull failure → register_transient + retry
```

**Failure scenario:** rsync drops the connection mid-transfer but exits 0 (a
known behaviour with `--timeout`). The truncated file passes `load_mono` for
any file that decodes enough to produce samples. `embed_track_per_measure`
runs on garbage audio, produces plausible-looking 1024-dim vectors, and
`push_mert_rows`/`push_set_mert_rows` ships them to canonical. The DB queue
predicate (`WHERE dim = 1024`) then considers the track done; the bad embeddings
are permanent until the next full re-embed campaign.

`track_audio.sha256` is populated at ingest time for all tracks in the
backfill queue (they already have a `track_analysis` row), so the check would
fire on the majority of tracks.

**Recommended fix:** import `sha256_file` from `loop_hardening` in both loops
and add the check after `rsync_in()`, matching the `vast_loop.py` pattern.

### [LOW / LATENT] C2 — MERT backfill loops: no transient retry, bare quarantine

**Files:** `scripts/mert_backfill_loop.py`, `scripts/set_mert_backfill_loop.py`
**Class:** C2 — transient vs poison-pill not distinguished

Both loops catch `subprocess.CalledProcessError` and immediately add the id to
`failed_tids`/`failed` with no retry:

```python
except subprocess.CalledProcessError as e:
    log.error("[%d] subprocess failed: %s", tid, e)
    n_failed += 1
    failed_tids.add(tid)
```

A single transient network glitch on `rsync_in` permanently quarantines the
track for the run. `loop_hardening.register_transient` / `transient_backoff_seconds`
exist exactly for this — `vast_loop.py` and `mac_analyze_loop.py` both use them.

The MERT backfill loops are typically run unattended for hundreds of tracks;
a network glitch early in the run silently reduces the completion count
without retry opportunity.

**Recommended fix:** import `register_transient`, `transient_backoff_seconds`
and wrap `rsync_in` failures as transient with bounded retries, matching the
`mac_analyze_loop.py` pattern.

### [LOW / LATENT] B1 — `scripts/acquire_variant.py`: yt-dlp call has no timeout

**File:** `scripts/acquire_variant.py`, line ~83
**Class:** B1 — missing subprocess timeout

```python
subprocess.run(cmd, check=True)   # no timeout=
```

yt-dlp has no internal timeout on the actual HTTP download. Bot detection
silently stalls the transfer; `subprocess.run` blocks the caller indefinitely.
This is an interactive one-shot script so the user can Ctrl+C, but the stall
is invisible until they notice.

**Recommended fix:** add `timeout=600` (or pull `SSH_PUSH_TIMEOUT` from
`loop_hardening`) to bound the call.

### [LOW / LATENT] B1 — `scripts/mac_push_acquire.py`: scp/ssh calls without timeouts or SSH_OPTS

**File:** `scripts/mac_push_acquire.py`, `_download` (line ~79) and
`_push_and_register` (lines ~109, ~117)
**Class:** B1 — missing subprocess timeout + missing SSH_OPTS

```python
# _download (line ~79)
subprocess.run(cmd, capture_output=True, text=True)  # no timeout

# _push_and_register (line ~109)
subprocess.run(["scp", ...], ...)                    # no timeout, no SSH_OPTS
subprocess.run(["ssh", PI_HOST, ...], ...)           # no timeout, no SSH_OPTS
```

`loop_hardening.SSH_OPTS` sets `ConnectTimeout` and `ServerAliveInterval`.
Without them, a stalled scp/ssh transfer hangs the Mac process indefinitely.

**Recommended fix:** import `SSH_OPTS, SSH_PUSH_TIMEOUT` from `loop_hardening`
and splice them into the scp/ssh calls, matching `mert_backfill_loop.py`.
