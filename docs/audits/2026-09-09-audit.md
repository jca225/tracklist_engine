### 3.1 HIGH (new) · C — `mac_analyze_loop.py` main-loop outer handler misses `subprocess.TimeoutExpired`

**File:** `scripts/mac_analyze_loop.py` · Line 517

**Class:** C (silent-failure / dishonest loop exit) + B (timeout-backstop path
not exercised correctly)

The main `while True` loop wraps each track in:

```python
try:
    rsync_in(remote_path, local_audio)   # check_call with timeout=RSYNC_TIMEOUT
    asset = fetch_asset(tid, local_audio) # ssh_pi → subprocess.run with timeout
    ...
except subprocess.CalledProcessError as e:
    if register_transient(tid, str(e), attempts, failed_tids, counts, log):
        n_seen += 1
    else:
        time.sleep(transient_backoff_seconds(attempts[tid]))
```

`subprocess.check_call(..., timeout=RSYNC_TIMEOUT)` (and `subprocess.run(...,
timeout=SSH_QUERY_TIMEOUT)`) raise `subprocess.TimeoutExpired` on wall-clock
timeout. `TimeoutExpired` inherits from `subprocess.SubprocessError`, NOT from
`CalledProcessError` — so the `except` clause does not catch it.

Consequence: a wall-clock timeout (e.g. Tailscale SOCKS tunnel silently hangs
— the primary case loop_hardening's `SSH_OPTS` ServerAlive probing is designed
to detect, at ~45 s) propagates uncaught through the `while True` loop, crashing
the entire `mac_analyze_loop` process instead of calling `register_transient` and
retrying. The `finally` block still runs (cleaning up the local file), but the
loop dies and requires a manual `tmux` restart.

**Severity:** HIGH — confirmed present. The RSYNC_IO_TIMEOUT (rsync's `--timeout`
flag, I/O-stall-based) normally fires first and exits rsync with nonzero
(→ `CalledProcessError`, handled correctly). The subprocess wall-clock timeout
(600 s) is the backstop for non-I/O stalls. That's a narrow window, but Tailscale
network resets without any I/O drop (e.g. a NAT rebind) would hit it.

**Fix:** Widen the except clause to catch the common superclass:
```python
except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:
```
or use `subprocess.SubprocessError` to cover both.

### 3.2 HIGH (carried from 3.4) · C — `mac_analyze_loop._persist_in_bg` exception scope too narrow

**File:** `scripts/mac_analyze_loop.py` · Line 419

**Class:** C3 (honest counting)

`_persist_in_bg` catches only `subprocess.CalledProcessError`:

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

A timeout in `rsync_stems_out` (which calls `subprocess.check_call` with
`timeout=RSYNC_TIMEOUT`) raises `TimeoutExpired`, not `CalledProcessError`.
The background thread then dies without calling `persist_failed_inc()`, so:
- The Counts tally underreports persist failures
- `exit_status()` may return exit 0 when it should escalate (C1 side-effect)
- The track has no `track_analysis` row, so it will be re-selected on the next
  run (no data corruption, but silent)

Note: the previous audit (3.4) also listed `OSError` (scratch DB path missing)
and `sqlite3.OperationalError` as uncaught in `_persist_in_bg`. Both remain open.

**Severity:** HIGH — confirmed present (same `TimeoutExpired` miss as 3.1 above).

**Fix:** Broaden the except clause to cover the relevant exception set:
```python
except (subprocess.SubprocessError, OSError, sqlite3.OperationalError) as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

### 3.3 MEDIUM (carried from 3.1) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~359–372

The GPU worker loop mode increments `n_done` on both success and failure paths
and always returns `exit 0` at both terminal conditions. Unlike `mac_analyze_loop`
which calls `loop_hardening.exit_status()`, `gpu_worker` has no equivalent — a
full-failure session exits 0 and any orchestrator (including `gpubox_agentic_both`)
sees success.

The previous audit (2026-07-27, 3.1) documented the fix: increment a separate
`n_failed` counter on the failure path and call `exit_status(n_done, n_failed)`
at both return sites. **Not yet fixed.**

### 3.4 LOW (carried from 3.2) · B — `mac_analyze_loop.py` sha256_file missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

`sha256_file(local_audio)` can raise `OSError` if rsync exits 0 but leaves a
zero-byte file (race). The call site has no try/except, so the OSError would
propagate out of the main try block and hit the `except subprocess.CalledProcessError`
handler — which also misses it (same exception-scope issue as 3.1). Result:
the exception propagates uncaught and crashes the loop.

`set_mert_backfill_loop.py` (now removed) had a guard; the pattern here is
missing. Fix: wrap with `try/except OSError`.

### 3.5 LOW · C1 — `ingest/main_retry.py` always returns exit 0

**File:** `ingest/main_retry.py` · Line 417

The Spotify retry entrypoint always returns 0, even when every candidate produces
a `db_failed` result (i.e., audio downloads but cannot be inserted into the
canonical DB — data loss). Lower severity because `main_retry` is a helper (not
the primary ingestion path), and failures are logged, but a CI-driven health
check would see success when it should alarm.
