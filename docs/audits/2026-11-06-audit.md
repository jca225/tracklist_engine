## 3. New findings

### 3.1 HIGH · B1/C2 — `mac_analyze_loop.py` main loop catches `CalledProcessError` but not `TimeoutExpired` → crash on network stall

**File:** `scripts/mac_analyze_loop.py` · Line 517 (main `while True:` except clause)

**Class:** B1 (hang / missing timeout recovery) + C2 (exception escapes, kills loop).

The main analysis loop has one `except` clause:

```python
        except subprocess.CalledProcessError as e:
            # Pull/ssh failures reaching here are transient (timeout, broken
            # pipe) — retry with backoff before quarantining (C2).
            if register_transient(tid, str(e), attempts, failed_tids, counts, log):
                n_seen += 1
            else:
                time.sleep(transient_backoff_seconds(attempts[tid]))
```

The comment names "timeout, broken pipe" as the intended catch, but
`subprocess.TimeoutExpired` is **not a subclass of `CalledProcessError`** — both
descend from `subprocess.SubprocessError` independently. When `rsync_in()` or any
SSH query hits its wall-clock timeout (`RSYNC_TIMEOUT=600`, `SSH_QUERY_TIMEOUT=120`),
Python raises `subprocess.TimeoutExpired`, which escapes this `except` block and
propagates to `main()` as an uncaught exception, **crashing the entire analysis
loop**.

The loop is designed to treat rsync/SSH timeouts as transient and retry with
backoff (the `register_transient` path). Instead, they crash the process.

**Scenario:** Tailscale connection stalls mid-transfer → rsync hits 600s backstop →
`TimeoutExpired` → crash instead of backoff + retry → entire Mac GPU session lost.

**Confirmed present.** No `TimeoutExpired` import or catch exists anywhere in
`mac_analyze_loop.py`.

**Fix:** change line 517 to:
```python
        except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:
```

The same gap appears in `_persist_in_bg` at line 419 (background thread only catches
`CalledProcessError`; a timeout there kills the thread silently — see open finding
3.4 from 2026-07-27, which flags the narrow except as Low — this escalates the
main-loop instance to High because the entire process crashes, not just one thread).

## 4. Open findings (carried)

### 4.1 MEDIUM · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~359–372

**Class:** C (silent-failure loop) — C3 honest-counting + C1 honest exit code.

`n_done` increments on the failure path:

```python
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1    # ← C3: done counter advanced on failure
    continue
...
n_done += 1        # success path
```

Both terminal conditions (`return 0` at line 337 for queue drain and line 372 for
`--max-tracks`) return 0 unconditionally. A session where every track fails logs
"done" and exits 0 — orchestrators/CI treat it as success.

**Fix:** separate `n_done` (success) from `n_failed` (failure); call
`exit_status(n_done, n_failed)` at both return sites, matching `mac_analyze_loop.py`'s
contract. *(Unchanged from 2026-07-27.)*

### 4.2 LOW · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

`sha256_file(local_audio)` can raise `OSError` (e.g., `FileNotFoundError`) if
rsync exited 0 but the file is missing. This propagates through the main loop's
except (which catches only `CalledProcessError`) and crashes the loop. Impact
lower than 3.1 because rsync exiting 0 without producing the output file is a
rare race; the network-stall scenario (3.1) is a more common trigger.

**Fix:** wrap `sha256_file` call in a `try/except OSError` or extend the main
`except` to also cover `OSError`. *(Unchanged from 2026-07-27.)*

---

### 4.3 LOW · C3 — `mac_analyze_loop.py _persist_in_bg` exception scope too narrow

**File:** `scripts/mac_analyze_loop.py` · Lines ~419–424

`_persist_in_bg` only catches `subprocess.CalledProcessError`. An `OSError` or
`subprocess.TimeoutExpired` during `rsync_stems_out` or `push_track_rows` kills
the background thread silently: `persist_failed_inc()` is never called, `Counts`
undercount failures, and the main loop re-picks the same track_audio_id (since
`track_analysis IS NULL`) and re-runs expensive GPU analysis unnecessarily.

**Fix:** widen to `except (subprocess.CalledProcessError, subprocess.TimeoutExpired, OSError)`.
*(Unchanged from 2026-07-27, but the main-loop instance of the same bug is now
promoted to HIGH above.)*
