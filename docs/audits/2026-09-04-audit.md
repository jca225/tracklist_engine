### New findings

#### M1 — Medium / latent · `mac_analyze_loop.py` · rsync transport bypasses `SSH_OPTS`

**File:** `scripts/mac_analyze_loop.py:171–202`  
**Bug class:** B1 (latent hardening gap)  
**Grade:** Medium — no data loss, but failure detection is 13× slower than intended.

`rsync_in()` and `rsync_stems_out()` both invoke rsync with `HOST:PATH` syntax, which uses SSH as the transport internally. Neither passes `-e "ssh <SSH_OPTS>"` to propagate the `BatchMode=yes`, `ConnectTimeout=15`, and `ServerAliveInterval/CountMax=15/3` settings from `loop_hardening.SSH_OPTS` into the rsync SSH layer.

**Consequence:** a silently-dead Tailscale TCP connection during a file transfer will stall for up to `RSYNC_TIMEOUT=600s` (the wall-clock subprocess backstop) instead of the intended ~45 s that three missed ServerAlive keepalives would detect via a direct `ssh` call. I/O timeout (`rsync --timeout=300`) only fires if no bytes flow at the application layer — a broken TCP session where the kernel still holds the socket open never triggers it.

**Failure scenario:** Tailscale connection drops mid-rsync → rsync hangs → no I/O → `--timeout 300` fires after 300 s → subprocess `timeout=600` fires only if the process hasn't exited → worst-case 600 s stall per file (vs. ~45 s with keepalive).

**Fix:** add `-e "ssh {' '.join(SSH_OPTS)}"` to both rsync calls, or define an `RSYNC_SSH_E` constant in `loop_hardening.py` and apply it consistently.

#### M2 — Medium / latent · `mac_analyze_loop.py:_persist_in_bg` · narrow except misses non-subprocess failures

**File:** `scripts/mac_analyze_loop.py:419–424`  
**Bug class:** C1 (silent failure / dishonest exit code)  
**Grade:** Medium — self-healing (track retried next run), but exit code can be wrong.

```python
except subprocess.CalledProcessError as e:
    counts.persist_failed_inc()
    log.error("[%d] (bg) push failed: %s", tid, e)
```

`push_track_rows()` makes two direct `sqlite3` calls against `SCRATCH_DB` (connect, execute, commit) before and after the SSH subprocess. A `sqlite3.OperationalError` (SCRATCH_DB missing, locked, or schema-corrupt) is not a `subprocess.CalledProcessError` and will propagate out of the background thread uncaught. The `finally` block still unlinks the local stems directory, but:

1. `counts.persist_failed_inc()` is **never called** → the loop's `exit_status()` sees `persist_failed=0` even though persist failed.
2. No error log is emitted for the failure.
3. `n_seen` was already incremented (at the `handed_off = True` point) but neither `done` nor `persist_failed` will ever be incremented → `exit_status` can return 0 (success) for a run where every push silently failed.

**Self-healing:** since the canonical DB never gets the `track_analysis` row, `next_task()` will re-queue the track on the next run.

**Failure scenario:** `SCRATCH_DB` becomes corrupt mid-run → every bg push raises `sqlite3.DatabaseError` → all threads die silently → loop drains with `done=0, failed=0, persist_failed=0` → `exit_status` returns `(0, INFO, "queue drained — analyzed 0, failed 0")` → caller sees exit 0 and logs a cheerful drain message.

**Fix:** broaden to `except Exception as e:` (or at minimum `except (subprocess.CalledProcessError, sqlite3.Error)`) and call `counts.persist_failed_inc()` in all paths.
