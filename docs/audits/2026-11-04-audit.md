### 3.1 MEDIUM (escalated) · C2/C3 — `mac_analyze_loop._persist_in_bg` misses `subprocess.TimeoutExpired` → infinite re-analysis

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424

**Class:** C2 (poison-pill retry) + C3 (honest counting)

The background push thread catches only `subprocess.CalledProcessError` —
not `subprocess.TimeoutExpired`, which is raised when any of the bounded
subprocess calls within (rsync mkdir @ 120s, rsync push @ 600s, sqlite3-over-ssh
push @ 300s) stall past their wall-clock limit:

```python
def _persist_in_bg(tid: int, stem_local: Path) -> None:
    try:
        rsync_stems_out(stem_local, tid)   # check_call with timeout=RSYNC_TIMEOUT
        push_track_rows(tid)               # run with timeout=SSH_PUSH_TIMEOUT
        counts.done_inc()
    except subprocess.CalledProcessError as e:  # does NOT catch TimeoutExpired
        counts.persist_failed_inc()
        log.error(...)
    finally:
        shutil.rmtree(stem_local, ...)
```

`subprocess.TimeoutExpired` is a sibling of `CalledProcessError` under
`subprocess.SubprocessError`; neither catches the other.

**When it fires:** a flaky Tailscale push (e.g. pushing 200–500 MB stems over a
degraded link) times out. The exception is swallowed by the thread, neither
`persist_failed_inc()` nor `done_inc()` is called, and the track's DB row is
never written to canonical.

**Consequence:** `next_task()` sees the same `track_audio_id` again (no
`track_analysis` row exists, `failed_tids` is never updated). The main loop
re-analyzes the same track (200–250 s on MPS) indefinitely, until the network
recovers enough for the push to succeed on a later iteration.

**Fix:** widen to `except (subprocess.CalledProcessError, subprocess.TimeoutExpired)`
or `except subprocess.SubprocessError` to match the full set of exceptions the
bounded calls can raise.

**Note:** this is an escalation of finding 3.4 from the 2026-07-27 audit, which
flagged the narrow except clause but characterized the consequence as
"undercount failures." The specific TimeoutExpired case causes *infinite re-analysis*,
not just undercounting, which raises severity from LOW to MEDIUM.

### 3.2 MEDIUM (carried from 2026-07-27 §3.1) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~324–372

```python
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1   # ← C3: done counter advanced on failure
    continue
n_done += 1       # ← success path, same counter
...
return 0          # ← C1: always exits 0, even when every track failed
```

A GPU box run where every track fails returns exit 0 and logs nothing alarming
to the queue-draining code path. `--max-tracks N` is exhausted by failures
alone. Compare: `mac_analyze_loop.py` calls `exit_status(n_done, n_failed)` from
`loop_hardening`.

**Fix:** track `n_failed` separately; call `exit_status(n_done, n_failed)` at
both return sites.

### 3.3 MEDIUM (new) · C1 — `ingest/main_retry._run()` always returns 0

**File:** `ingest/main_retry.py` · Lines 411–417

```python
_log.info(
    "DONE | candidates=%d downloaded=%d timeout=%d gone=%d other=%d db=%d in %.0fs",
    stats.candidates, stats.downloaded, stats.failed_timeout,
    stats.failed_unavailable, stats.failed_other, stats.db_failed, elapsed,
)
return 0
```

Regardless of `stats.db_failed` (insert failures), `stats.failed_timeout`
(spotdl stalls), or a run where `downloaded=0` with `candidates>0`, `_run()`
returns 0. A cron or script-driven invocation treats all-failure runs as
success. The same violation exists in `gpu_worker.py` (finding 3.2 above) and
was fixed in `mac_analyze_loop.py` via `loop_hardening.exit_status()`.

**Fix:** compute a failure ratio at the end of `_run()` and return nonzero
(+ `logging.ERROR`) when `downloaded == 0` and `candidates > 0`, or when
`db_failed / candidates` exceeds a threshold. The `loop_hardening.exit_status`
helper already encodes this logic.

### 3.4 LOW (carried from 2026-07-27 §3.2) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Lines ~454–463

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

An `OSError` here propagates uncaught, killing the main thread for that track
and leaving `persist_failed_inc()` uncalled. Impact: low (rsync must exit 0 and
the file must become unreadable in the same window), but the sibling
`set_mert_backfill_loop.py` already has this guard:

```python
try:
    local_sha = sha256_file(local_audio)
except OSError as exc:
    local_sha = f"<unreadable: {exc}>"
```

### 3.5 LOW (carried from 2026-07-27 §3.3) · C2 — backfill loops quarantine on first `CalledProcessError`, no bounded retry

Neither `mert_backfill_loop.py` nor `set_mert_backfill_loop.py` imports
`register_transient` from `loop_hardening`. A single transient SSH or rsync
failure immediately quarantines the track for the session. `mac_analyze_loop.py`
uses 3-attempt bounded retry + exponential backoff before permanent quarantine.

---

### 3.6 LOW (carried from 2026-07-27 §3.5) · B — `set_mert_backfill_loop.push_set_mert_rows` splits one logical write across two SSH transactions

`push_set_mert_rows` issues `set_mert_measures` INSERTs in one `BEGIN IMMEDIATE`
transaction and the `analyzer_versions_json` UPDATE in a separate SSH call. If
the second call fails, `set_mert_measures` rows exist but the version metadata
is permanently stale (the queue predicate won't re-queue since `dim=1024` is
satisfied). `mert_backfill_loop.push_mert_rows` does both in one transaction —
this loop should match that pattern.
