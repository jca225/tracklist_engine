## 3. Open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` loop mode always exits 0

**File:** `analysis/gpu_worker.py` · Lines 334–337, 364, 369, 372

**Class:** C — C1 (dishonest exit code) + C3 (honest counting).

`n_done` is incremented on both success and failure paths (lines 364, 369):

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # ← C3: done counter advanced on failure too
    continue
n_done += 1
```

Both terminal conditions (queue drained, `--max-tracks` hit) return 0
unconditionally — the function does not call `loop_hardening.exit_status()`.
Contrast `mac_analyze_loop.py` which calls `exit_status(done, failed, pf)` and
escalates to nonzero+ERROR when `n_done == 0` or failure ratio exceeds 50%.

Consequence: a GPU box run where every track fails (corrupt audio, bad DB path,
missing file) exits 0 with INFO "no unanalyzed tracks remain". The gpubox
orchestrator tears down the box and sees success. No analysis rows produced.

**Fix:** track `n_failed` separately; call `exit_status(n_done, n_failed)` at
both return sites. Matches the `loop_hardening` contract already used by
`mac_analyze_loop.py`.

### 3.2 LOW (carried) · B — `mac_analyze_loop.py` sha256 check missing `OSError` guard

**File:** `scripts/mac_analyze_loop.py` · Line 455

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

An `OSError` (file vanishes between rsync completing and the sha read) would
propagate uncaught through the main `try` block. The outer `except
CalledProcessError` at line 517 does NOT catch `OSError`, so the exception
reaches the outermost `while True` and kills the analysis thread — without
calling `persist_failed_inc()`. The loop hangs on `bg.join()` next iteration
indefinitely since no bg thread was launched.

Mitigation: the race window is tiny and `--timeout`+subprocess timeout already
bound the rsync. Grade: Low / latent.

### 3.3 LOW (carried) · C3 — `mac_analyze_loop.py _persist_in_bg` exception scope too narrow

**File:** `scripts/mac_analyze_loop.py` · Lines 409–424

`_persist_in_bg` catches only `subprocess.CalledProcessError`:

```python
def _persist_in_bg(tid: int, stem_local: Path) -> None:
    try:
        ...
        push_track_rows(tid)
        counts.done_inc()
    except subprocess.CalledProcessError as e:
        counts.persist_failed_inc()
        log.error(...)
    finally:
        ...
```

An `OSError` (scratch DB path missing) or `sqlite3.OperationalError` (lock
timeout) would terminate the bg thread silently without calling
`persist_failed_inc()`. The Counts tally then underreports persist failures,
and `exit_status` may see a false-clean ratio.

**Fix:** broaden to `except (subprocess.CalledProcessError, OSError,
sqlite3.OperationalError)` or catch `Exception` with a narrow re-raise on
`KeyboardInterrupt`.

### 3.4 LOW (new) · C1 — `ingest/main_retry.py` always returns 0

**File:** `ingest/main_retry.py` · Lines 353, 417

`_run()` returns 0 whether downloads succeeded or all failed:

```python
_log.info("DONE | candidates=%d downloaded=%d timeout=%d ...", ...)
return 0   # ← always, even if downloaded=0 and all timed out
```

No exit-code escalation on complete failure, unlike the analysis loops which
use `loop_hardening.exit_status()`. If Spotify API credentials are expired and
every download times out, CI/cron sees exit 0.

Impact: lower than 3.1 — this is a one-shot manual retry script, not a
continuous loop with an orchestrator. Grade: Low / latent.
