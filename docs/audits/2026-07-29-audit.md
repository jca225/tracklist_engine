## 2. Semantic findings

### 2.1 Class A — Encoding / mojibake at SSH/sqlite boundaries

**[A1] `core/ssh_sqlite.py:28-33` — text=True without encoding=; no wall-clock timeout; incomplete SSH opts**
Grade: **Medium · latent/hardening**

```python
# core/ssh_sqlite.py:27-34
cmd = ["ssh", "-o", "ConnectTimeout=15", host, f"sqlite3 {db}"]
out = subprocess.run(
    cmd,
    input=script,
    capture_output=True,
    text=True,          # ← no encoding= — uses platform locale
    check=True,
    # ← no timeout= — stalled SSH connection hangs indefinitely
)
```

Three compounded gaps in the canonical shared primitive:

1. **No `encoding="utf-8", errors="surrogateescape"`**. When pi-storage's locale
   is non-UTF-8 (the pi issue #74 context), sqlite3 emits non-ASCII bytes in
   track names/paths that Python decodes via the platform default, raising
   `UnicodeDecodeError` or silently producing mojibake. Callers include
   `labeling/acquire/reconcile_aligning_manifest.py` and
   `labeling/acquire/inventory_check.py` — both are invoked during labeling
   workflow, so a corrupt decode kills a manual ground-truth session.

2. **No wall-clock subprocess `timeout=`**. Only `ConnectTimeout=15` covers the
   initial TCP handshake; a connection that succeeds but then stalls
   (broken Tailscale pipe, server overload) blocks indefinitely. This is
   exactly bug B1 from the founding audit.

3. **Incomplete SSH opts**. Missing `ServerAliveInterval=15`, `ServerAliveCountMax=3`,
   `BatchMode=yes` — the `SSH_OPTS` list `loop_hardening.py` exports for
   precisely this purpose. A dead connection is detected in ~45 s with those
   opts; without them the subprocess just hangs.

`loop_hardening.py` covers this pattern for `mac_analyze_loop`'s SSH calls, but
`core/ssh_sqlite.py` was promoted from a labeling helper and never adopted the
hardening.

Fix: add `encoding="utf-8", errors="surrogateescape"` to the subprocess call;
add `timeout=SSH_QUERY_TIMEOUT` and expand the SSH opts list to include
`ServerAliveInterval`, `ServerAliveCountMax`, `BatchMode=yes`. Import from
`scripts.loop_hardening` or duplicate the constants directly (core imports
nothing upward).

### 2.3 Class C — Silent-failure loops

**[C1] `analysis/gpu_worker.py:370-372` — `--loop --max-tracks` exits 0 when dominated by failures**
Grade: **Low · latent**

```python
# gpu_worker.py:326-372 (loop mode)
while args.max_tracks is None or n_done < args.max_tracks:
    ...
    if not r.is_ok():
        ...
        failed_tids.add(track_audio_id)
        n_done += 1      # ← counts failure as done
        continue
    ...
    n_done += 1          # ← counts success
_log.info("hit --max-tracks=%d, stopping", args.max_tracks)
return 0                 # ← always 0, regardless of failure ratio
```

`n_done` increments on *both* success and failure, so `--max-tracks=5` stops
after 5 attempts whether all succeeded or all failed. Unlike `mac_analyze_loop`
which calls `exit_status()` (the C1 fix from `loop_hardening`) and returns
nonzero when failures dominate, `gpu_worker` always exits 0 after `--max-tracks`
is reached. A smoke run that hits all 5 failures is indistinguishable from a
clean run to the calling orchestrator.

This only affects `--loop --max-tracks` (smoke testing). Single-track mode and
unlimited loop mode are unaffected (they return 1 on any failure and 0 only when
drained-clean respectively).

Fix: call `exit_status(n_done - len(failed_tids), len(failed_tids))` before the
final `return 0`; or rename `n_done` to `n_seen` (matching mac_analyze_loop's
nomenclature) to make the dual-counting explicit and add a separate `n_succeeded`
for the exit gate.
