## 3. Open findings

### 3.1 MEDIUM (carried) · C1+C3 — `gpu_worker.py` increments `n_done` on failure, always returns 0

**File:** `analysis/gpu_worker.py` · Lines ~356–372 (unchanged since 2026-07-27)

**Class:** C (silent-failure loop) — C3 honest-counting + C1 honest exit code.

`n_done` is incremented on both the failure path and the success path:

```python
r = _process_one(a, args.db, ar2.value, resolved, args.stems_dir)
if not r.is_ok():
    _log.warning("FAIL track_audio_id=%s: %s", track_audio_id, r.error)
    failed_tids.add(track_audio_id)
    n_done += 1          # C3: done counter advanced on failure
    continue
_log.info("OK [%d] ...", n_done + 1, ...)
n_done += 1
```

Both exit points (`return 0` at line 337 when queue is drained; `return 0` at
line 372 when `--max-tracks` is hit) are unconditional, with no `exit_status()`
call. Consequences:

1. A session where every track fails logs "done" and returns exit 0 — cron /
   a caller treats it as success. Compare: `mac_analyze_loop.py` calls
   `exit_status(done, failed)` which escalates to nonzero + ERROR when all work
   fails or failure ratio exceeds 50%.
2. With `--max-tracks N`, ten consecutive failures exhaust the limit with zero
   actual records written; the caller receives exit 0.

**Fix (unchanged from 2026-07-27 recommendation):** split `n_done` into
`n_done` / `n_failed`; advance only `n_failed` on the failure path; call
`exit_status(n_done, n_failed)` at both return sites.

### 3.2 LOW (carried) · B — `mac_analyze_loop.py:455` sha256_file without OSError guard

**File:** `scripts/mac_analyze_loop.py` · Line ~455

```python
if asset.sha256:
    local_sha = sha256_file(local_audio)   # no try/except OSError
    if local_sha != asset.sha256:
```

An `OSError` (e.g. rsync exits 0 but the file is not present due to a race)
propagates uncaught past the `except subprocess.CalledProcessError` guard,
falls through to the outer `except subprocess.CalledProcessError as e:` at
line 517, and triggers `register_transient` — so the track retries rather than
being quarantined. The practical impact is low (rsync success + missing-file
race is rare), but the behaviour is surprising and inconsistent with
`set_mert_backfill_loop.py`'s guarded version of the same pattern.

### 3.3 LOW (carried) · C3 — `mac_analyze_loop.py _persist_in_bg` catches only `CalledProcessError`

**File:** `scripts/mac_analyze_loop.py` · Lines ~409–424

```python
def _persist_in_bg(tid: int, stem_local: Path) -> None:
    try:
        ...
        push_track_rows(tid)
        counts.done_inc()
    except subprocess.CalledProcessError as e:
        counts.persist_failed_inc()
        log.error("[%d] (bg) push failed: %s", tid, e)
    finally: ...
```

An `OSError` (scratch DB path missing) or `sqlite3.OperationalError` (lock
timeout overrun) would kill the background thread without calling
`persist_failed_inc()`. The honest-counting guarantee (C3) breaks: the Counts
tally underreports failures, and the main loop continues without knowing the
persist thread died. The fix is to widen the except clause to
`except (subprocess.CalledProcessError, OSError, Exception)` (or at minimum
`Exception`) and call `persist_failed_inc()` in all error branches.
